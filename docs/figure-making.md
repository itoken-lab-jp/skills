# figure-making

AI に「この構成を図にして、SVG で」と頼むと、部品とつながりは合った図が返ってきます。ところが開いてみると、矢印のラベルが線に乗っている、長い名前が箱からはみ出している、ということがよくあります。AI は座標を計算して置くだけで、描いた結果を見ていないからです。架空の場面で Skill（AI が読む手順書）を入れない AI に試させると、SVG の構成図と流れ図は6回とも、こうした小さな崩れを残して渡しました。Mermaid のシーケンス図は3回とも構文エラーで、GitHub では図の代わりにエラーが出る状態でした（下の「Skill を入れずに頼むと」）。

figure-making は、コードで書く図とスライド（SVG・HTML・Mermaid で書く構成図・流れ図・シーケンス図・見出し画像・スライド）を AI に作らせるときの、AI が読む手順書（Skill）です。Skill は、エージェントが作業に合わせて読み込む手順書のファイルです。重ならない置き方を守らせ、同梱の検査の道具で描かせて、文字の重なり・はみ出し・線が文字を通る所・Mermaid の構文エラーを数で出させ、描いた画像を AI 自身に開かせて、直してから渡させます。

向いているのは、Claude Code や Codex などのエージェントに、資料に貼る図、README の図、HTML のスライドを作らせている人です。画像生成（絵を描く AI）の話ではありません。データのグラフ、Web の画面、PowerPoint のファイル（.pptx）そのものは扱いません。図の型や決まりがあるリポジトリでは、AI はそちらに従います。

## 使い方

Claude Code・Codex など、Skill の共通の形式（[Agent Skills](https://agentskills.io/specification)。フォルダーに手順書の `SKILL.md` を置く形）を読むエージェントで使えます。入れておくと、エージェントは Skill の説明文（どんなときに読むか）を見て、次のような頼みで読み込みます。

- 「system.md の構成を構成図にして。architecture.svg で」
- 「このメモを部会で映すスライド1枚にして。16:9 の HTML で」
- 「ログインの流れを Mermaid のシーケンス図にして、docs に書いて」

確実に読ませたいときは「figure-making の Skill に従って」と名前で頼みます。

検査の道具（`scripts/layout-check.mjs`）は、Node 22 以上と、Chrome・Edge・Chromium のどれかがあれば動きます。npm のパッケージは要りません。Mermaid を描くときだけ、mermaid.js を近くの `node_modules` か CDN から読みます（読むのはライブラリだけで、図の中身は外に送りません）。人が手で走らせることもできます（下は、公開リポジトリを clone した場所からの例。`npx skills add` で入れたときは、入れた先の `figure-making/scripts/` にあります）。自分の PC のブラウザで動くかは、手元の SVG を1つ渡してみると分かります。

```
node skills/figure-making/scripts/layout-check.mjs architecture.svg
node skills/figure-making/scripts/layout-check.mjs deck.html --pdf deck.pdf
node skills/figure-making/scripts/layout-check.mjs README.md --width 900
```

出力は、描いた PNG の場所と、「線が文字を通っている：「書き込み」（x 793, y 365）」のような指摘の一覧です。指摘があれば終了コードは 1 です。機械で分かるのは文字の箱と線の位置だけなので、線のからまりや余白の偏りは、画像を開いて見ます。

## Skill を入れずに頼むと

架空の場面で、Skill を入れない AI に同じ頼みを3回ずつさせました。作った図は、AI から見えない検査がブラウザで描いて、重なりとはみ出しを測りました（場面の中身と数え方は、下の「試した結果」）。

- 構成図と流れ図（SVG）は、6回とも小さな崩れが残りました。矢印のラベル（「書き込み」「在庫の照会」「不備なし」）が線に乗る、長い名前が箱や枠からはみ出す、迂回の線が文字にかかる、の3種類です。6回とも、描いた図を画像にして見ていません。画像にする道具（ImageMagick の `convert`）が動かないと、そこで確かめるのをやめて、「重なりが無いか確認してください」と頼んだ人に回しました。
- Mermaid のシーケンス図は、メッセージの中のセミコロン（`Cookie（HttpOnly; Secure; SameSite=Lax）`）が行の区切りと読まれて、3回とも構文エラーになりました。3回とも描いて確かめておらず、1回は「そのまま図として表示されます」と言い切りました。流れ図のほうは、ラベルを引用符で囲んでいて、3回とも描けました。
- メモを1枚のスライドにする場面は、3回ともはみ出しは無く、収まっていました。ただ、本文が 18px と小さいまま下半分が空いていて、2回はメモの数字を自分の計算で書き換えました。
- 数枚のスライドを PDF にする場面は、3回とも用紙の大きさと改ページを最初から正しく書いていました。箱が3つの簡単な図と、見出し画像（PNG）は、崩れなく作れました。この3つの場面で Skill が足すのは、描いた画像を見て確かめることだけです。

## SKILL.md に書いてあること

AI が読むファイルです。使うだけなら読まなくてかまいません。どう動くかを確かめたいときは [SKILL.md](../skills/figure-making/SKILL.md) を開いてください。

- 描く前に、伝えることを1つ決めます。スライドは見出しを結論の文にし、入りきらなければ文字を縮めずに、載せるものを減らすか枚数を分けて、省いたものを返事に書きます。元の資料の数字は書き換えません。
- 大きさと文字の下限を先に決めます（図は 14px、映すスライドの本文は 24px、見出し画像の題は 56px）。
- 重ならない置き方：箱の幅は文字数から決める、矢印のラベルは線に乗せず横に離す、斜めの線に沿って文字を回さない、戻りの線は外側に通り道を取って線ごとにずらす、多くの部品へ引く線はまとめの枠か印と凡例にする。
- HTML のスライドは固定の大きさの箱にし、PDF で配るなら用紙の大きさと改ページを書きます。
- 書いたら毎回、検査を走らせ、指摘を直し、描いた PNG を自分で開いて見ます。「検査して直す」は3回までで、残った崩れは場所を返事に書きます。画像にする道具が1つ動かなくても、次の手段を試します。
- Mermaid：置く先が Mermaid を描く所（GitHub など）の流れ図・シーケンス図は Mermaid で書きます。ラベルは引用符で囲み、シーケンス図の `;` は `#59;` と書くなど、記号を逃がします。検査が構文エラーを出します。

## 参考にしたもの

書く前に、skills.sh で多く入れられている図・スライドの Skill と、研究を読みました。文は写していません。インストール数は 2026年11月15日の skills.sh の値です。

- [anthropics/skills](https://github.com/anthropics/skills) の pptx（Apache License 2.0、約26万）：描いてから画像にして見る手順を必須にしている。見た目を測る検査は無い。
- coleam00 の excalidraw-diagram（約9千。ライセンスは確かめられず）：PNG に描いて見て直すのを 2〜4 回。
- jimliu の baoyu-diagram（MIT、約1.6万）：間隔を数値の決まりで守る。
- zarazhangrui の frontend-slides（MIT）：入らなければ文字を縮めずにスライドを分ける。
- スライドの配置の研究（arXiv 2502.15412、AutoPresent 2501.00912）：コードを見直すより、描いた画像を見て直すほうが、配置が良くなる。
- スライドの見出しを主張の文にする（assertion-evidence）：[Penn State の資料](https://writing.engr.psu.edu/research.html)。

| 取り入れた所 | 取り入れなかった所 |
|---|---|
| 描いた画像を自分で見て直す、直す回数に上限を置く | テーマ・配色・装飾の決まり（好みによるため） |
| 間隔を数値で決める、入らなければ分ける | pptx のファイルを作る手順 |
| 見出しを結論の文にする | 図を描く専用の道具（Excalidraw など）への依存 |

読んだ Skill には、描いた図の文字の箱を測って、重なりとはみ出しを数で出す道具は見当たりませんでした（子を親に収める検査を持つものが1つあると解説で読みましたが、ソースは確かめていません）。日本語の折り返しと Mermaid の記号の逃がし方も、読んだ中にはありませんでした。この2つと検査の道具が、この Skill で足した所です。

## 試した結果

2026年11月に、架空の場面で試しました。作業する AI（Claude の Sonnet）は、元の資料を置いたフォルダーの中で作業します。作業のあと、AI から見えない検査が、作った SVG・HTML・Mermaid を Chromium で描いて、文字どうしの重なり、枠からのはみ出し、線が文字を通る所、Mermaid の構文エラー、PDF のページ数と用紙を測りました。描いた画像と測った結果と作業の記録は、Skill の有無を伏せて、別の AI（Claude の Opus）が画像を開いて採点しました。場面ごとに守ってほしいこと（観点）を決め、それぞれを満たしたかを見ました。

- 場面1：部品が12ほどあるシステムの構成（監視の線が多い、名前が長い）を、SVG の構成図にする。観点は6個。
- 場面2：差し戻しが3本と分かれ道がある経費精算の流れを、SVG の流れ図にする。観点は6個。
- 場面3：1枚には多すぎる振り返りのメモを、16:9 の HTML のスライド1枚にする。観点は6個。
- 場面4：提案を 5〜6 枚の HTML のスライドにし、PDF で配れる形にする。列の多い表がある。観点は6個。
- 場面5：「集める → 整える → 見せる」の3つの箱の図。落とし穴の無い場面で、Skill を入れたせいで重くならないかを見る。観点は5個。
- 場面6：40字ほどの長い題の、記事の見出し画像を 1280×670 の PNG で作る。観点は6個。
- 場面7：ステップの名前にかっこ・引用符・コロン・`end` が入った注文の流れを、README に Mermaid の流れ図で入れる。観点は5個。
- 場面8：メッセージにセミコロンや波かっこが入ったログインの流れを、Mermaid のシーケンス図にする。観点は5個。

観点は、たとえば場面1なら「部品とつながりが漏れず、作り話が無い」「文字どうし、文字と線が重なっていない」「文字が箱や図の外にはみ出していない」「線がからまず、文字が小さすぎない」「描いた図を画像にして自分で見てから渡した」「返事が短い」です。表の数字は、満たした観点の数を3回分足したものです。分母は観点の数×3回です。採点は観点ごとに「満たした・一部だけ・満たさない」の3段で、表は「満たした」だけを数えています。観点は Skill の書き手が決めたもので、重みは同じに置いています。独立に試したのは場面ごとに3回です。

| 場面 | Skill なし | Skill あり |
|---|---|---|
| 1 構成図（SVG） | 6/18 | 13/18 |
| 2 流れ図（SVG） | 8/18 | 15/18 |
| 3 メモを1枚のスライドに | 7/18 | 18/18 |
| 4 数枚のスライドと PDF | 12/18 | 15/18 |
| 5 3つの箱の図（落とし穴なし） | 9/15 | 13/15 |
| 6 見出し画像（PNG） | 15/18 | 15/18 |
| 7 Mermaid の流れ図 | 9/15 | 12/15 |
| 8 Mermaid のシーケンス図 | 2/15 | 12/15 |

- 採点したのは人ではなく AI です。重なり・はみ出し・構文エラー・PDF のページ数は、採点とは別に機械で測っています（次の項目）。「Skill あり」は、Skill の本文を必ず読ませた条件です。Skill なしで落とした観点の多くは「描いた図を自分で見てから渡した」で、場面1〜5・7・8の21回のうち、描いた図を画像で見られたのは0回でした（2回は画像への変換を試して失敗し、そこでやめました。場面6は PNG を作る頼みなので、3回とも開いて見ました）。Skill ありは24回とも、描いた画像を開いて見ました。
- AI から見えない検査が拾った崩れは、場面1・2の Skill なしで6回中6回、Skill ありで6回中1回でした（枠の見出しが枠から少しはみ出した1回。作業した AI が見た画像と、検査の側の描画でフォントが違い、文字の幅が変わったためです）。場面8の構文エラーは、Skill なしで3回中3回、ありで0回でした。ただし Skill ありの2回は、セミコロンを `#59;` で逃がさずに、読点や「/」に言い換えて避けました（言い換えたことは返事で伝えています）。
- Skill ありで残った外しは、ほとんどが「返事が短い」です（24回のうち18回が「一部だけ」）。図の読み方や構成の一覧を返事に重ねて書きます。場面2では、差し戻しの3本を1本の線にまとめて、どこから戻るのかが見えにくくなった回が2回ありました。
- 表の数字は、公開した版の1つ前の版のものです。表を取ったあと、Skill を少し直しました（確かめ用の PNG を図の横に残さない、余白を詰めすぎない理由、日本語の折り返し）。直した版で場面1と5を3回ずつやり直すと、14/18 と 13/15 で、検査が拾った崩れは6回とも 0 でした。ほかの場面は、直した版ではやり直していません。
- Skill を置くだけにして、読むかどうかを AI に任せた条件も、場面1〜4・6〜8で1回ずつ試しました（作者が使っているほかの Skill 35本と一緒に置いた状態）。7回ともこの Skill を読み、観点は 34/40 でした。図のある README の誤字を直すだけの頼みでは、読みませんでした。
- 1回の費用と時間（Skill なし → あり）は、場面1が 0.10〜0.11 ドル・57〜64秒 → 0.10〜0.28 ドル・61〜163秒、場面3が 0.04 ドル・24〜28秒 → 0.04〜0.09 ドル・28〜42秒、場面8が 0.02 ドル・15〜16秒 → 0.08〜0.13 ドル・36〜59秒、落とし穴の無い場面5が 0.02 ドル・14秒 → 0.02〜0.03 ドル・18〜20秒でした。描いて検査して画像を見る分が増えます。
- PlantUML は、この Skill に入れていません。Skill なしで2つの場面（シーケンス図を SVG に、構成図を PNG に。描く道具の jar を置いた状態）を3回ずつ試すと、6回とも手元の jar で描き、構文エラーも無く、公開のサーバーに図を送ることもありませんでした。構成図の3回は、Graphviz が無いために出たエラーの絵に自分で気付いて、配置の指定を変えて描き直し、PNG を開いて見ました。この6回は採点にかけておらず、作業の記録と描いた図を書き手が見た結果です。PlantUML が描いた SVG は、検査の道具にそのまま渡せます。
- 確かめていないこと：検査の道具は Linux の Chromium で動かしただけで、Windows と Mac の Chrome・Edge では、公開の CI の試験で確かめます。見た目の好み（配色・雰囲気）は測っていません。作業する AI が Sonnet 以外のとき、Claude Code 以外のツールで読み込まれるかは、確かめていません。日本語のフォントは描く PC で変わるので、検査で指摘が無くても、見る人の PC で文字の幅が変わることがあります。

## 入れ方

```
npx skills add itoken-lab-jp/skills -g --skill figure-making
```

`-g` は、プロジェクトごとではなく、自分のユーザーのどのプロジェクトでも使える場所に入れる指定です。手順の本文は [SKILL.md](../skills/figure-making/SKILL.md) です。入れ方の詳しい説明（置かれる場所、ツールごとの違い）は [README](../README.md#入れ方) にあります。
