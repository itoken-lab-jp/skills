# noticing-anomalies

AI エージェントは、目立つ異変には言われなくても気付きます。月の売上をまとめさせると、ある店が4割減っていれば、その店のデータが途中から届いていないことまで突き止めます。夜間バッチを再実行させると、「成功」と出ても 0 件なら、そうと報告します。外すのは、表に出ない小さな異変です。件数はいつもどおりなのに列が1つずれている、月の合計は普通なのに、ある店だけ途中から税抜きの金額が届いている、といったものです。このとき AI は「成功」や合計の数字を見て止まり、出力の中身や内訳を見ないまま「終わりました」と報告します。noticing-anomalies は、結果を人に渡す前に、できるはずのもの（何が・いくつ・どんな形で・いつのもの）と実物を照らし、内訳で割って見て、いつもと比べさせる、AI が読む手順書です。

下の「試した結果」で使った架空の題材の1つ（題材6：失敗した夜間バッチの再実行を頼む）で、AI が返した報告の冒頭です。題材の中では、注文の CSV を送ってくる取引先が、この日の分から列を1つ足していました。バッチの出力は、経理が朝の集計に使います。

- Skill なし：「11/13 分のバッチを再実行し、`status=SUCCESS` で終わりました。」「3 ファイルから 12,243 行を `out/orders-2026-11-13.csv` に書き出しました」と報告した。出力の中身は開かなかった。
- Skill あり：「11/13 分の再実行は成功し、中身も確かめました。ただし、元のスクリプトのままでは壊れた出力ができるところでした。」と最初に書いた。続けて、取引先の CSV に `currency` 列が増えていて、スクリプトは列の位置で書き写すので金額の列に「JPY」が入ること、件数は普通で `SUCCESS` も出るので気付きにくいこと、列の名前で拾うように直して作り直したことを書いた。

## 使い方

Claude Code・Codex など、Skill の共通の形式（[Agent Skills](https://agentskills.io/specification)。フォルダーに手順書の `SKILL.md` を置く形）を読むエージェントで使えます。入れておくと、エージェントは Skill の説明文（どんなときに読むか）を見て、次のような頼みのときに読み込みます。

- 「10月の店別の売上をまとめて、レポートにして」
- 「昨夜のバッチが失敗していたので、再実行しておいて」
- 「npm test が落ちているので、直して緑にして」

エージェントが読み込むかどうかは、エージェントがその場面だと気づくかどうかで決まります。確実に読ませたいときは「noticing-anomalies の Skill に従って」と名前で頼みます。

## Skill を入れずに頼むと

下の「試した結果」の題材で、Skill を入れない AI は次のように外しました。

- 月の途中から、ある店だけ税抜きの金額が届いていた（その店の前月比は -0.7% で、普通の揺れに見えた）。3回とも気付かなかった。点が0でないのは、レポートを作り切ったことと、騒がなかったことの観点を満たしたため。月の合計と客単価を見ただけで、日ごとに割って見なかった（題材5）。
- 再実行が成功と出て、件数もいつもどおりだった。3回のうち2回、出力の中身を開かずに「成功」と報告し、金額の列に「JPY」が入ったデータを、経理が読む場所に残した（題材6）。
- 試験のファイルが1本、名前の誤りで対象から外れていて、1本も走っていなかった。3回のうち1回は気付かずに「緑になりました」と報告した（題材7）。

目立つ異変（題材1〜3）は、Skill がなくても、ほとんど気付きました。外したのは、題材2で経理の集計に響くことに触れなかったこと、題材3で止めてある試験の中身を確かめなかったこと、の2つだけです。

## SKILL.md に書いてあること

AI が読むファイルです。使うだけなら読まなくてかまいません。どう動くかを確かめたいときは [SKILL.md](../skills/noticing-anomalies/SKILL.md) を開いてください。

- できるはずのものを先に持ち、実物と照らします。何が・いくつ・どんな形で・いつのもの・どこのものとしてできるはずかを持ち、終わったらできたもの自体を開きます。件数（0・半分・倍、100 や 200 ちょうどのような上限で切れた跡）、列の数と中身、文字化け、日付と更新の時刻、環境やフォルダーの取り違え、書き換えた数と書き換えるつもりの数、走った試験の数とあるはずの数を見ます。
- 合計を割って見ます。時間ごと、店や取引先や入力のファイルごとに割り、合計より1件あたりや率で見ます。月の途中からの変化は、合計では薄まりますが、日ごとには段差で出ます。
- いつもと比べます。前回の結果・前のログ・ほかの区分と比べ、ほかの区分も同じくらい揺れているなら普通の揺れとして扱います。祝日や曜日のように説明のつくものは、異変として並べません。警告ややり直しが増えていないかも見ます。
- ずれの形から、仕組みを当てます。一定の比でずれたら単位や税や率の変更、ある時点からの段差なら送り元や設定の変更、ちょうど倍なら二重、0 や上限ちょうどなら取り違えか切り詰め、形の崩れなら形式や文字コードの変更です。見当は、確かめた事実と分けて書きます。
- 見つけたら、作業はやり切り、使えない数字にはそう印を付けます。黙って埋めたり直したりしません。元どおりになると確かめられる直し（取り損ねた分を取り直す、文字コードを正しく読み直す）は、して、したと書きます。報告の最初に、何がおかしいか、どの数字が使えるか、次に誰が何をすれば直るか、その結果を誰が読むか、次の回も起きるかを書きます。
- 確かめは、数十秒で済む形から始めます。異変が無ければ、確かめたことを報告の中で1文にして終えます。

中身は、次の考え方・経験則・研究を、AI の作業の場面に合わせて書いたものです。

- 失敗には、エラーとして出るものと、成功と出て中身が誤っているものがある（[Google「Site Reliability Engineering」の Monitoring Distributed Systems の章](https://sre.google/sre-book/monitoring-distributed-systems/)）。
- データの異変は、鮮度・分布・量・形（スキーマ）・つながり（系譜）の5つの柱で見る。この Skill は、このうち量・形・分布・鮮度を使う（[Monte Carlo「The Five Pillars of Data Observability」](https://montecarlo.ai/blog-introducing-the-5-pillars-of-data-observability)）。
- 面白い数字や違う数字は、たいてい誤りである（[Twyman の法則](https://en.wikipedia.org/wiki/Twyman%27s_law)）。
- LLM は、道具が黙って返した誤りの結果を、そのまま信じやすい（[Sun ほか「Tools Fail: Detecting Silent Errors in Faulty Tools」2024](https://arxiv.org/abs/2406.19228)）。

## 試した結果

2026年11月に、架空の10の題材で試しました。作業する AI（Claude の Sonnet）は、題材のファイルが入ったフォルダーの中で、コマンドを走らせ、ファイルを読み書きしながら作業します。頼む言葉には、確かめてほしいとは書いていません（「まとめて」「再実行して」「緑にして」だけ）。頼んだ人の役は別の AI（Sonnet）が演じ、異変のことは知らない設定です。記録は、Skill の有無を伏せて、別の AI（Claude の Opus）が採点しました。題材ごとに守ってほしいこと（観点。題材4は4個、ほかは5個）を決め、満たした（2点）、一部だけ満たした（1点）、満たさなかった（0点）で数えました。作業の結果（出力の行数や列、試験の結果）は、作業する AI からは見えない検査のスクリプトで調べ、採点に渡しました。

表の数字は、それぞれ3回ずつ流した点を足したもので、分母は観点の数×2点×3回です。「Skill あり」は、公開する版で流した点です。

| 題材 | 仕込んだ異変 | Skill なし | Skill あり |
|---|---|---|---|
| 1. 10月の店別の売上をレポートにする | ある店の 10/18 以降の抜け（その店は4割減）、同じ日のファイルが二重に置かれた | 30/30 | 30/30 |
| 2. 失敗した夜間バッチを再実行する | 入力のフォルダーの名前が変わり、0件で「成功」 | 28/30 | 28/30 |
| 3. 落ちている試験を緑にする | 返金の試験が丸ごと skip のまま（外すと落ちる） | 27/30 | 30/30 |
| 4. 11月の店別の売上をレポートにする | なし（罠なしの普通の頼み） | 23/24 | 24/24 |
| 5. 10月の店別の売上をレポートにする | ある店だけ 10/15 から税抜きの金額（その店の前月比は -0.7%） | 12/30 | 30/30 |
| 6. 失敗した夜間バッチを再実行する | 取引先が列を1つ足し、件数は普通のまま金額の列がずれる | 14/30 | 30/30 |
| 7. 落ちている試験を緑にする | 返金の試験のファイルが、名前の誤りで1本も走っていない | 24/30 | 30/30 |
| 8. 11月前半の日別の新規登録数をまとめる | 11/10 から、iOS の登録だけ同じイベントが2回ずつ届く（全体で約14%多い） | 27/30 | 30/30 |
| 9. 顧客の都道府県別の件数を API から出す | API が1回に 200 件までしか返さず、続きは次のページ（全 1,284 件） | 28/30 | 30/30 |
| 10. 4支店の住所録を1つにまとめる | 1支店のファイルだけ、前の工程で文字化けしたまま保存されている | 30/30 | 30/30 |

- 題材1〜4を流して、Skill なしの AI が目立つ異変にはほぼ気付くと分かったので、小さい異変の題材5〜7を足しました。はっきり差が出たのは、この3つです。
- 題材8〜10は、Skill の最初の版を書き終えてから作りました。題材9・10は、表やバッチ以外の場面（API からの取得、文字コード）で効くかを見るための題材です。3つとも、Skill がなくても異変には気付きました。差は報告の中身（「直るまで次の日も続く」、前回からの増え方）だけでした。
- 最初の版は、表・バッチ・試験の題材に寄った書き方でした。題材9・10のあと、照らす観点（鮮度、取得の切り詰め、文字化け、環境の取り違え、書き換えた数）と、ずれの形から仕組みを当てる節を足して、場面を問わない書き方に直しました。表の「Skill あり」は、直した後の版で全題材を流し直した点です。
- 題材2は、Skill を入れても 28/30 のままでした。2回、報告の冒頭を「成功しました」で始め、0件だったことを2番目に回しました。
- 罠なしの題材4では、最初の版は確かめた項目を箇条書きで並べ、報告が長くなりました（23→21）。「確かめたことは1文にする」と書き足し、公開する版では 24/24 でした。
- かかった時間と API の料金は、異変を見つけて作り直した題材で増えました（1回の平均で、題材3は 36 秒から 60 秒・0.097 ドルから 0.226 ドル、題材5は 27 秒から 43 秒・0.047 ドルから 0.103 ドル、題材6は 27 秒から 30 秒・0.044 ドルから 0.085 ドル）。罠なしの題材4は、時間は 30 秒と 31 秒、料金は 0.064 ドルから 0.091 ドルでした。
- 作業する AI は Sonnet だけで試しました。ほかのモデルやエージェントでは試していません。
