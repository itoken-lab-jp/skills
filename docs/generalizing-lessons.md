# generalizing-lessons

AI エージェントは、具体の例から原則を取り出すことはできます。レビューで修正された箇所を「同じ種類の問題」にまとめたり、いくつかの事例から原則を立てて手引きを組んだりします。外すのは、そこから戻って確認する一歩です。事例や差分から手引き・学びを書かせると、作った原則を、作るときに使っていない例に当てて確認し、外れた所で原則を修正する、という往復をしません。そのため、原則が手元の例に縛られ、次に使う人が別の場面に当てにくくなります。generalizing-lessons は、この往復（具体→抽象→具体）をさせる、AI が読む手順書です。レビューの指摘を文書の残りに当てる仕事は、下の試験では Skill がなくてもよくできたので、効くのは主に手引き・学び・チェックリストを書く仕事です。

もう1つ外すのは、規則を書かれていない場面に当てる仕事です。Skill なしの AI は、規則を言葉のとおりに当て、規則ができた理由を読みませんでした。下の「試した結果」の題材6（本番にプログラムを反映してよいかの相談に、チームの規則に照らして答える依頼）では、「金曜日には本番に反映しない」という規則（理由は、反映のあと見る人がいない）を、木曜だが翌日から担当が 11 日間いない反映に「木曜なので可」と当てました。この Skill は、例や規則がそうなっている理由（本質）を先に抜き出し、言葉でなく理由で当てさせます。当ててみて言葉と理由がずれていたら、規則の言葉の修正も提案させます。

下の「試した結果」の題材2で、AI が書いた手引きの違いです。題材2は、4件の障害の振り返り（売上の日報が2倍になっていた、夜間の処理の出力件数が3分の1だった、テストの件数が減っていた、1つの支店の売上だけが1,000倍だった）から、新人向けの「数字や結果のおかしさに気づく手引き」を書く依頼です。それぞれ3回ずつ流しました。

- Skill なし：「ちょうど2倍なら二重の取り込み、約3分の1なら一部しか読んでいない、約1,000倍なら単位の違い」のように、4件から原則を立てた。ただし原則を4件の外に当てて確認せず、原則が当てはまらない場合（休日で本当に少ない、など）にも触れなかった（3回とも）。
- Skill あり：同じ原則を立てたうえで、4件以外の場面に当てて確認した。たとえば「API で一覧を取ったらちょうど 200 件だった（1回に返す上限で切れている）」は「切りのよい数は仕組みの跡を疑う」に、「移行の処理が『0 件更新』で成功した」は「『成功』の印を中身の数で確かめる」に当たる、と書いた。原則が当てはまらない場合（休日、確認済みのキャンペーン、「いつも」の値がまだ無い新しい処理）も書いた（3回とも）。

## 使い方

Claude Code・Codex など、Skill の共通の形式（[Agent Skills](https://agentskills.io/specification)。フォルダーに手順書の `SKILL.md` を置く形）を読むエージェントで使えます。入れておくと、エージェントは Skill の説明文（どんなときに読むか）を見て、次のような依頼のときに読み込みます。

- 「1節目にレビューが付いたので、指摘を踏まえて文書全体を直して」
- 「この4件の振り返りをもとに、新人向けの手引きを書いて」
- 「AI の下書きと私が直した版の差分から、学びを残して。次の記事からも使う」
- 「今週の相談4件に、チームの決まりに照らして可否を返して」
- 「この細かい決まりの一覧を、初めての場面でも使える形に組み直して」

エージェントが読み込むかどうかは、エージェントがその場面だと気づくかどうかで決まります。確実に読ませたいときは「generalizing-lessons の Skill に従って」と名前で依頼します。

## SKILL.md に書いてあること

AI が読むファイルです。使うだけなら読まなくてかまいません。どう動くかを確認したいときは [SKILL.md](../skills/generalizing-lessons/SKILL.md) を開いてください。

- 上がる（本質を抜き出す）：例ごとに、何を変えたかでなく、なぜそうなっているかを1文で書きます。規則や前例は、できた経緯を探して読みます。2つ以上の例を比較して理由の共通点を本質の文にし、例に出てくる物の名前を使わずに言い直します。新しい場面を見て当たるか当たらないかを決められる高さにします。
- 下りる（別の場面の形に落とす）：作るときに使っていない例（文書の残り、隣のファイル、相談されている場面）に当てます。探すときも判断するときも、例や規則の言葉でなく本質で見ます。時間や金額の線を引く所は、線の両側の値を1つずつ挙げます。修正するのに要る事実（数字・連絡先など）が手元に無ければ、作らずに【要確認】のような印を付けて残し、報告で聞きます。
- 横に広げる（食い違う例を探す）：見た目は似ているが当てはまらない例と、見た目は違うが当てはまる例を1つずつ探します。この2つを本質の文だけで仕分けられなければ、上がる所に戻ります。
- 修正する：拾うべき所を拾えなかったら本質の文を広げ、拾ってはいけない所を拾ったら当てはまらない場合を書き足します。元の規則の言葉が理由とずれていたら、言葉の修正を1〜2行で提案します（自分の持ち物でない規則は書き換えません）。当てて修正する一巡で本質の文が変わらなければ止め、変わり続けても3巡で止めます。
- 残す：原則ごとに、理由、典型の修正前と修正後の例を1つ、当てはまらない場合を付けます。手引きの見出しは原則で組み、事例ごとの節にはしません。細かい規則の一覧を組み直すときは、元の規則を捨てずに、どれかの原則の下に置きます。修正や事例が3つ以上並んだら、並べて終える前に一度上がります。
- 1か所だけの決まった修正（名前の変更、誤字）では、この手順を回しません。規則を当てる場面で、経緯を読んで理由を1文にした結果、言葉と理由が食い違わなければ、あとの手順は省きます。

中身は、次の研究と考え方を、AI の作業の場面に合わせて書いたものです。

- LLM は規則を作るのは得意だが、自分で作った規則を個々の例に当てるのは苦手（[Qiu ほか「Phenomenal Yet Puzzling: Testing Inductive Reasoning Capabilities of Language Models with Hypothesis Refinement」ICLR 2024](https://arxiv.org/abs/2310.08559)）。
- 人でも、例が1つだと原則は別の場面に移らず、2つ以上を比較すると移る（Gick・Holyoak「Schema induction and analogical transfer」Cognitive Psychology、1983）。比較する学び方の効果をまとめた分析（Alfieri・Nokes-Malach・Schunn「Learning Through Case Comparisons」Educational Psychologist、2013）。
- 初心者は問題を見た目の特徴で分け、熟達者は原理で分ける（Chi・Feltovich・Glaser「Categorization and Representation of Physics Problems by Experts and Novices」Cognitive Science、1981）。人が例を思い出すときは見た目の似た例に引かれるが、役に立つと判断するのは関係の形が同じ例（Gentner・Rattermann・Forbus「The Roles of Similarity in Transfer」Cognitive Psychology、1993）。
- LLM も、見た目が似ているだけの例に引かれる。関係の形が同じで見た目が遠い例を、見た目が近い紛らわしい例から選び分ける課題で、GPT-4 は 29.1%、人は 91.4% だった（[Sourati ほか「ARN: Analogical Reasoning on Narratives」](https://arxiv.org/abs/2310.00996)）。
- 例は概念を広げ、少しだけ違う外れ（near miss）は概念を絞る（Winston の MIT 6.034 の講義「Learning: Near Misses, Felicity Conditions」）。境界は、線の両側の値で示す（[Adzic「Focus on key examples」](https://gojko.net/2014/05/05/focus-on-key-examples/)）。
- 具体から抽象に上がり、また具体に下りる（細谷功『具体と抽象』『「具体⇔抽象」トレーニング』）。
- 原則だけに書き直すと、例で当たっていた修正が当たらなくなった（日本語の文章の Skill を作ったときの観察）。そのため、原則には典型の例を残します。

## 試した結果

2026年11月に、架空の5つの題材で試しました。作業する AI（Claude の Sonnet）は、題材のファイルが入ったフォルダーの中で、ファイルを読み書きしながら作業します。依頼した人の役は別の AI（Sonnet）が演じます。記録は、Skill の有無を伏せて、別の AI（Claude の Opus）が採点しました。題材ごとに守ってほしいこと（観点）を決め、満たした（2点）、一部だけ満たした（1点）、満たさなかった（0点）で数えました。修正した箇所が残っているかは、作業する AI からは見えない検査のスクリプトで数え、採点に渡しました。

表の数字は、それぞれ3回ずつ流した点を足したもので、分母は観点の数×2点×3回です。

| 題材 | Skill なし | Skill あり |
|---|---|---|
| 1. 1節目に付いたレビューの指摘3つを踏まえて、使い方の文書全体を修正する（2節以降に、同じ原則に当たる箇所が言葉を変えて9つある） | 33/42 | 34/42 |
| 2. 4件の障害の振り返りから、新人向けの「数字や結果のおかしさに気づく手引き」を書く | 24/36 | 36/36 |
| 3. AI の下書きと人が修正した版の差分から、学びを残す（同じフォルダーに次の記事の下書きがある） | 26/36 | 32/36 |
| 4. 文書のボタンの名前を1か所修正する（罠なしの普通の依頼） | 24/24 | 24/24 |
| 5. FAQ の2問に付いたレビューを踏まえて、FAQ 全体を見直す | 35/36 | 35/36 |

- 効いたのは、事例や差分から手引き・学びを書く題材（2・3）です。Skill なしは、原則を作ったあと、ほかの例に当てて確認することをしませんでした（題材2で3回とも、題材3で3回のうち2回。残る1回も、次の記事の下書きを読んで備考で触れただけでした）。Skill ありは、作るときに使っていない例に当てて確認し、原則が当てはまらない場合も書きました。
- レビューの指摘を文書全体に生かす題材（1・5）は、Skill がなくてもよくできました。指摘を種類に分け、残りの節にも当てました。題材1では、Skill のあるなしにかかわらず、「何の設定か書く」という指摘を「保存先を選びます」「前の版に戻します」には当てませんでした（修正したのは3つのうち1つ）。
- 題材5は、Skill の最初の版を書き終えてから作りました。最初の版は、題材1で1回、仕様として言い切るべき文（「1 円でも違えば変換の誤りです」）を和らげ、気づいた抜けを黙って残すこともあったので、「当たらない側の例も探して変えない」「直すのに要る事実が無ければ印を付けて残す」を追加しました。表の「Skill あり」は追加した後の版の点です。追加したあと、題材1で言い切りを和らげた回は無くなりましたが、「何の設定か」の抜けを拾う数は変わりませんでした。Skill の中の例は、どの題材とも違う場面（コードの引数の名前）で書いています。
- 題材3の Skill ありで残った減点は、次の記事の下書きに当てて外れが無く、原則を修正しなかった回（観点では「一部」に数えた）と、修正前と修正後の例が欠けた原則があった回です。
- 題材1の Skill なしの点は、検査のスクリプトの誤り（修正した文に元の言葉が含まれると「直していない」と数える）で下がった分を戻しています。
- かかった時間は、題材1で 25 秒から 29 秒、題材2で 41 秒から 48 秒、題材3で 34 秒から 44 秒に増え、題材4・5は変わりませんでした（18〜19 秒、31 秒）。API の料金は、1回あたり約 0.02〜0.06 ドルから 0.04〜0.09 ドルに増えました。手順を回さない依頼でも Skill の本文を読む分は増えるので、短い依頼ほど割合が大きく、罠なしの題材4では時間は同じで料金が約2倍でした。

各3回の小さな試験で、作業したのは Claude の Sonnet だけです。ほかのモデルやエージェントでは試していません。どれも1回の依頼で終わる題材で、長い作業の途中で自分から原則に上がるかは試していません。題材を作った人と Skill を書いた人が同じで、題材1の結果を見て Skill を修正してもいるので、Skill が得意な題材に寄っているおそれがあります。Skill のあるなしで良くなる向きを見るための数字で、どの仕事でもこの割合で効くという意味ではありません。

## 入れ方

```
npx skills add itoken-lab-jp/skills -g --skill generalizing-lessons
```

`-g` は、プロジェクトごとではなく、自分のユーザーのどのプロジェクトでも使える場所に入れる指定です。手順の本文は [SKILL.md](../skills/generalizing-lessons/SKILL.md) です。入れ方の詳しい説明（置かれる場所、ツールごとの違い）は [README](../README.md#入れ方) にあります。
