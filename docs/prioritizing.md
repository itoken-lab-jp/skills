# prioritizing

AI エージェントは、1件ずつの作業は上手にこなします。たまった Issue を片付けさせても、締め切りの近い不具合から修正し、もう直っている Issue や重複している Issue を閉じます。外すのは、全部は入らないときの絞り方と、作業の終わりに「ほかに何かある？」と聞かれたときです。たとえば、見積もりの合計が 25.5 人日（1人で1日かかる量が 1 人日）のやることを、2人×4日＝8 人日で終える計画を依頼すると、入らないことには気づきます。それでも目玉の機能を自分で「必須」に入れ、使える日を目いっぱい埋めた日程を出します。目玉を次に回すか、リリースの日をずらすかは、依頼した人が決めることです。「ほかに何かある？」と聞かれると、気づいたことを5〜7個並べ、「続けてやりましょうか」と作業を申し出ます。prioritizing は、全部は入らないときに「やらない」を先に決めさせ、削り方を依頼した人に1つにして渡させる、AI が読む手順書です。

下の「試した結果」の題材2（12/4 のリリースまでに、2人×4日でやることの計画を依頼する）で、AI が返した計画の冒頭です。題材の中では、新機能の「定期購入」が 4 人日、その試験が 1.5 人日です。

- Skill なし：「出荷に必須の項目だけで 12.5 人日あり、この 4 日では収まりません。」と書いた。この 12.5 人日には、自分で必須に入れた定期購入の 5.5 人日が入っている。依頼した人に決めてほしいことは4つに分かれ、どれを勧めるか（推奨）は書かなかった。
- Skill あり：「12/4 までに全部は入りません。…試験や手戻りの余白を 2〜3 割残すと、実際に使えるのは 5.5〜6 人日です。決めてほしいこと：定期購入（4 + 試験 1.5 = 5.5 人日）を 12/4 に入れるか。推しは、定期購入を後続のリリースに回す案です。」

## 使い方

Claude Code・Codex など、Skill の共通の形式（[Agent Skills](https://agentskills.io/specification)。フォルダーに手順書の `SKILL.md` を置く形）を読むエージェントで使えます。入れておくと、エージェントは Skill の説明文（どんなときに読むか）を見て、次のような依頼のときに読み込みます。

- 「Issue がたまってきたので、今日1時間で片付けられるだけ片付けて」
- 「このメモが来週のリリースまでにやること。計画にして」
- 作業の終わりに「ほかに何かある？」と聞く。

エージェントが読み込むかどうかは、エージェントがその場面だと気づくかどうかで決まります。確実に読ませたいときは「prioritizing の Skill に従って」と名前で依頼します。

## Skill を入れずに依頼すると

下の「試した結果」の題材で、Skill を入れない AI は次のように外しました。

- 入る量より多い計画（題材2・4）で、入らないことには気づくのに、目玉の機能や大きな対策を自分で「必須」や日程に入れた。削るか日をずらすかを、依頼した人に1つにして出さなかった。
- 使える日を目いっぱい埋め、試験や手戻りの余白を残さなかった（題材2で3回とも）。
- 変更履歴のファイル（CHANGELOG）を読めば「もう直っている」と分かる項目を、自分で読まずに質問として依頼した人に回した。
- 「ほかに気になったことある？」と聞かれると、新しい作業を5〜7個並べ、「続けて進められます」と申し出た（題材1で3回とも）。

一方で、たまった Issue を片付ける本題（題材1）は、Skill がなくてもよくできました。締め切りの近い不具合を最初に直し、直っている Issue と重複している Issue を根拠つきで閉じ、新しい Issue はほとんど作りませんでした。

## SKILL.md に書いてあること

AI が読むファイルです。使うだけなら読まなくてかまいません。どう動くかを確認したいときは [SKILL.md](../skills/prioritizing/SKILL.md) を開いてください。

- 先に量を比較します。使える時間と見積もりの合計を比較し、入らなければ最初の1文でそう言います。使える量の2〜3割は余白に残します。
- 並べる前に、やらなくてよいものを除きます。もう済んでいるもの（変更履歴のファイルや git の履歴で確認する）、同じ話のもの、前提が崩れたもの（依頼した人が異動した、長く動きがない）です。確認は手元で済ませ、人には聞きません。前提が崩れたものは、自分では閉じず、閉じてよいかを持ち主に聞く案として出します。
- 遅れたときの損で並べます。外の期限、遅れるほど損が広がるもの、ほかの作業の前提になるものが先です。番号順や易しい順では並べません。
- 範囲・期限・目玉の機能を落とすか、日をずらすかは、依頼した人が決めます。お金や契約が絡むものは、依頼した人かその上が決めます。選択肢と推奨を付け、決めてほしいことを1つに絞って出し、計画は推奨の案で組んで見せます。
- 追加しません。作業中に気づいたことは1件ずつ Issue や作業にせず、急ぐ順に1〜3点だけ書きます。「ほかに何かある？」にも同じように答え、依頼されていない作業を申し出ません。
- 1件を修正するだけの依頼では、この手順を回しません。

中身は、次の研究と考え方を、AI の作業の場面に合わせて書いたものです。

- 人は良くしようとすると追加する案ばかり考え、引く案を見落とす（[Adams ほか「People systematically overlook subtractive changes」Nature、2021](https://www.nature.com/articles/s41586-021-03380-y)）。LLM にも同じ偏りがある（[Santagata・De Nobili「More is More: Addition Bias in Large Language Models」2024](https://arxiv.org/abs/2409.02569)）。
- 遅れたときの損（Cost of Delay）を手間で割って並べる（Donald Reinertsen『The Principles of Product Development Flow』）。
- 先に使う時間を決め、入らない範囲を削る（[Basecamp「Shape Up」の appetite](https://basecamp.com/shapeup/1.2-chapter-03)）。

## 試した結果

2026年11月に、架空の4つの題材で試しました。作業する AI（Claude の Sonnet）は、題材のファイルが入ったフォルダーの中で、コマンドを走らせ、ファイルを読み書きしながら作業します。Issue は GitHub の代わりに、試験用に作った Issue の一覧の道具で扱います。依頼した人の役は別の AI（Sonnet）が演じます。記録は、Skill の有無を伏せて、別の AI（Claude の Opus）が採点しました。題材ごとに守ってほしいこと（観点。題材1・2・4は10個、題材3は4個）を決め、満たした（2点）、一部だけ満たした（1点）、満たさなかった（0点）で数えました。Issue の数や修正した結果は、作業する AI からは見えない検査のスクリプトで数え、採点に渡しました。

表の数字は、それぞれ3回ずつ流した点を足したもので、分母は観点の数×2点×3回です。

| 題材 | Skill なし | Skill あり |
|---|---|---|
| 1. Issue が 15 件たまった請求書の道具を、1時間で片付ける（最後に「ほかに気になったことある？」） | 53/60 | 60/60 |
| 2. 25.5 人日分のリリースのやることを、2人×4日（8 人日）で計画にする | 35/60 | 57/60 |
| 3. Issue を1件だけ修正する（罠なしの普通の依頼） | 23/24 | 23/24 |
| 4. 障害の振り返りで出た 23 日分の対策を、監査までの火・木の6日で計画にする（最後に「ほかに気になることある？」） | 35/60 | 57/60 |

- 題材4は、Skill の最初の版を書き終えてから作り、最初の版で流して 56/60 でした。そのあと、題材2と4で残った失敗に合わせて「変更履歴のファイルも読む」「お金や契約が絡むものは頼んだ人かその上が決める」「前提が崩れたものは自分では閉じない」を追加しました。表の「Skill あり」は4題材とも修正した後の版の点で、題材4は 57/60 でした。Skill の中の例は、どの題材とも違う場面（顧客デモの前の修正）で書いています。
- 罠なしの題材3では、一つ前の版で点が少し下がりました（23→21）。1回は一覧を見たのに締め切りの近い別の不具合に触れず「急ぐものは他にありません」と書き、1回は依頼されていない丸め方の判断を推奨つきで返しました。そこで、見ていない所について「無い」と言い切らない一文を追加し、題材3だけ流し直して 23/24（Skill なしと同じ）になりました。表の題材3の「Skill あり」はこの点です。残った1点は、Skill なしと同じく、近くにある別の不具合に触れなかったことです。題材1・2・4は、この一文を追加する前の版の点です。
- かかった時間は、どの題材でも Skill を入れて増えませんでした（平均で、題材1は 65 秒から 56 秒、題材2は 48 秒から 46 秒、題材3は 23 秒のまま、題材4は 50 秒から 45 秒）。API の料金は、1回あたり題材1で約 0.22 ドルから 0.17 ドル、題材2で 0.087 ドルから 0.091 ドル、題材3で 0.040 ドルから 0.065 ドル、題材4で 0.115 ドルから 0.151 ドル（約3割増え）でした。Skill の分だけ読む量が増えるので、短い依頼ほど割合が大きく増えます。
- Skill ありでも残った失敗は、量を比較するときに、外したあとの数字だけを書いて全体の見積もりと比較しない回があることです（題材2・4で各1回）。

各3回の小さな試験で、作業したのは Claude の Sonnet だけです。ほかのモデルやエージェントでは試していません。題材を作った人と Skill を書いた人が同じで、題材4の結果を見て Skill を修正してもいるので、Skill が得意な題材に寄っているおそれがあります。Skill のあるなしで良くなる向きを見るための数字で、どの計画でもこの割合で効くという意味ではありません。

## 入れ方

```
npx skills add itoken-lab-jp/skills -g --skill prioritizing
```

`-g` は、プロジェクトごとではなく、自分のユーザーのどのプロジェクトでも使える場所に入れる指定です。手順の本文は [SKILL.md](../skills/prioritizing/SKILL.md) です。入れ方の詳しい説明（置かれる場所、ツールごとの違い）は [README](../README.md#入れ方) にあります。
