# 業務の文書の作法

社内資料・報告・提案・依頼・お知らせ・メール・チャット・手順書・議事録・スライドに適用する。会社や文書の規則がある場合はその規則を優先する。規則が無い場合は1本の文書の中で統一する。検査スクリプトの `style`・`keigo`・`kana` が、このうち機械的に検査できる項目を示す。

## 場面ごとの既定

会社の規則と、相手との普段のやり取りの調子を優先する。この表は規則が無い場合の出発点である。

| 場面 | 文体と距離 | 順番 | 長さと形 | 必ず入れる |
|---|---|---|---|---|
| 社外のメール | です・ます。敬語は定型どおり。挨拶「お世話になっております」、結び「よろしくお願いいたします」。依頼・断り・質問にはクッション言葉 | 宛名 → 挨拶 → 名乗り → 用件の1文 → 詳細 → 結び → 署名 | 1通に1件。段落は数行で区切り、段落の間を1行空ける | 件名に用件と期限。相手にしてほしいこと、期限、問い合わせ先 |
| 社内のメール・上司への報告 | です・ます。挨拶は「お疲れさまです」の1行。尊敬語・謙譲語は軽く | 結論 → 依頼事項 → 根拠 → 次の作業 | 社外より短くてよい。内容が複雑な場合は箇条書き | 判断を求める場合は、対象と期限 |
| チャット（Teams・Slack） | です・ます を崩しすぎない程度に軽く。宛名と長い挨拶は省く | 1行目で用件（挨拶は用件と同じ投稿に） | 1投稿にまとめる。長くなる場合は箇条書きにするか、別の文書にしてリンクを貼る | 返信の要否と期限。詫びと複雑な断りはチャットで済ませない |
| 全社・部署へのお知らせ | です・ます。前提知識の無い人にも分かる言葉で、ていねいに親しみやすく。「ございます」は使わない | 変更の内容と開始日 → 読み手の作業 → 例外 → 問い合わせ先 | 見出しと箇条書きで、必要な箇所を探せる形にする | 対象者、期限、担当（無いと後回しにされる） |
| 提案・稟議 | です・ます か である（会社の様式に従う）。判断は「〜を勧めます」と言い切る | 決定を求める事項と期限 → 推奨案と理由 → 他の案 → リスクと対策 → 決定しない場合の影響 | 決裁者が1枚目で判断できる形にする。根拠のデータは必要なものを添付する | 目的、費用、時期、効果、リスク |
| 報告・障害報告 | です・ます。事実と推測を書き分ける | [文書の型](#文書の型) の報告・障害報告 | 経過は時刻つきの箇条書き | 現在の状態、影響の範囲、次の作業（担当者と期限） |
| 詫び・断り | です・ます。敬語はていねいに。言い訳を先に書かない | [文書の型](#文書の型) の詫び・断り | 短くしすぎない。相手の手間への一言を入れる | 起きたこと（断りでは結論）、今後の対応（断りでは代替案） |
| 手順書・ヘルプ | です・ます で「〜します」「〜してください」。敬語は重ねない（「ご確認いただけますようお願いいたします」より「確認してください」） | 前提 → 手順（1ステップ1操作）→ 完了の確認方法 | 番号を付ける。見出しから流れを追える形にする | 各手順の結果、失敗した場合の戻し方 |
| 議事録 | である か体言止め（社外に送るものは です・ます）。評価の言葉（「活発な議論が行われた」）を書かず、事実を書く | 決定事項 → 未決の事項 → 担当者と期限のある課題 → 論点と経緯 | 発言を書き起こさず、要点を書く | 日時、出席者、決定事項、未決の事項、課題 |
| スライド | 体言止めでよい。タイトルは言い切りの1文 | 1枚に主張を1つ | 文字数を減らし、大きく表示する。根拠と例は付録に置く | タイトルを順に読んで論旨が通ること |
| 仕様書・設計書・社内の docs | である か です・ます（リポジトリの規則に従う）。距離は近くなくてよい | 目的 → 結論（決定事項）→ 詳細 → 見送った事項 | 見出し・表・コードの例を使う | 読み手の次の作業、前提の版 |
| README | です・ます か である。初めて使う人を読み手とする | 用途 → 導入方法 → 使用方法 → 問題が起きた場合の対処 | コードの例を多く載せる | 前提（OS・版）、動作の確認方法 |
| 記事・ブログ | です・ます。書き手の判断と体験を書いてよい | 読み手の場面 → 結論 → 本文 → まとめ | 段落を詰めすぎない。説明は文でつなぎ、並列の項目は箇条書きか小見出しで拾える形にする | 対象の読者、読後にできること |

## 文体

- です・ます か である かを、1本の文書の中で統一する（箇条書き・表・体言止めは数えない）。社外への文書・依頼・お知らせ・メールは です・ます、社内の仕様書・設計書・議事録は である や体言止めが多い。スライドは体言止めでよい。
- 1文はおおむね100字まで、読点は1文に3つまで。超える場合は、2文に分けるか、語順を変えて読点を減らす。
- 漢字が7字以上続く箇所には、ひらがなを挟む（「業務効率化推進施策検討」→「業務の効率化を進める施策の検討」）。固有名詞・役職・法令名・機関名（「代表取締役社長」「個人情報保護法」）は変更しない。
- 二重否定（「〜ないことはない」）は、断定できる場合は断定する。確認できていないことを示す「〜ないとは言えない」は、不明な点を書く（「影響が無いことは未確認です」）。
- ら抜き言葉（見れる・来れる・食べれる）を使わない。
- 1文に逆接の「が、」を重ねない。「検討しましたが、今回は見送ります」のような1回の「が、」と、クッション言葉の「恐れ入りますが、」は使ってよい。
- 「〜を行う」「〜を実施する」「〜ことになります」は、動詞で書けるかを確認する（「変更を行う」→「変更する」）。「会議を行う」「監査を実施する」のように、動詞にできない名詞は変更しない。
- 事実と推測を書き分ける。推測には「〜と見ています」「〜の可能性があります」を付け、根拠を添える。

## 敬語

- 敬語の定型は残す（挨拶・結び・詫び・依頼・クッション言葉）。簡潔にすることと、敬語を削ることは異なる。
- 二重敬語を避ける（おっしゃられる → おっしゃる、拝見させていただく → 拝見する、ご利用になられる → ご利用になる）。
- 謙譲語を相手の動作に使わない（ご確認してください → ご確認ください、ご利用できます → ご利用いただけます、拝見してください → ご覧ください）。
- 社外に向けて、自分の側（社内の人）に尊敬語を使わない（「弊社の部長がおっしゃいました」→「弊社の部長が申しておりました」）。
- 「させていただく」を重ねない。「お送りいたします」「確認いたします」で足りる箇所は置き換える。「辞退させていただきます」「欠席させていただきます」のような定型は使ってよい。
- 宛名：個人は「様」、会社・部署は「御中」、複数の人は「各位」（「各位様」「御中様」と重ねない）。
- 自分の会社は「弊社」、相手の会社は書き言葉で「貴社」、話し言葉で「御社」。目上や社外への返事は「承知しました」「かしこまりました」。
- 社内の文書に、社外向けの重い敬語を使わない。

## 表記

- 英数字は半角、カナは全角。
- ひらがなで書くことが多い語（文化庁「公用文作成の考え方」から、頻出の語）。
  - 補助動詞：〜てください、〜ていただく、〜ておく、〜てみる、〜ていく
  - いたします（「お願い致します」の「致」）、できる（「出来る」）、ございます
  - 形式名詞：こと、ところ、もの、ため、よう（時を表す「時」は漢字でもよい）
  - 文の頭の接続詞：ただし、なお、したがって、また
  - 副詞の一部：ほとんど、ぜひ、あらかじめ、よろしく
- 「及び・並びに・又は・若しくは」は公用文と法令では漢字。一般の業務文書では「および」「または」でもよく、1本の文書の中で統一する。
- 英字と日本語の間の空白、カタカナ語の長音（サーバー／サーバ）、括弧の全角・半角は規則に従う。規則が無い場合は1本の文書の中で統一する。
- 画面の言葉（ボタン・メニュー・項目の名前・表示される文）は、画面と一字一句同じにし、「」で囲む。
- 略語は、初出の箇所に正式名を添える（「BCP（事業継続計画）」）。
- 箇条書きの文末は、1つの箇条書きの中で統一する（すべてを体言止めにするか、すべてを文にする）。
- 感嘆符（！）は、社外の文書・報告・手順書では使わない。

## 数字と日付

- 数字は半角。4桁以上は3桁ごとにカンマを入れる（1,200件）。金額は税込か税抜かを書く。
- 日付は曜日を添える（2026年11月12日（木））。曜日は暦で確認する（暗算では誤る）。「明日」「来週」のような相対的な表現は、日付に置き換える（読む日によって指す日が変わる）。
- 期限は日時まで書く（「11月25日（水）17時まで」）。
- 範囲は「以上・以下・未満・超」を使い分ける（「3万円以上」は3万円を含む、「3万円未満」は含まない）。

## 文書の型

最初の数行で、何についての文書かと、読み手への依頼の有無が分かるようにする。

- 報告：結論（起きたことと結果）→ 相手への依頼 → 根拠・経緯 → 次の作業。
- 作業報告：日付のある作業（追加・修正・確認）は、日付と件名の表か箇条書きにまとめる。本文には、現在の状態（何ができるようになったか）、分かったこと、残っている課題を書く。状態は現在形で書く（「PDF の表を CSV に書き出せます。」）。過去の作業を本文に書く場合は「〜しました」と書き、「〜しています」に言い換えない。読み手への依頼が無い場合は、依頼が無いことを書かない。
- 障害報告：起きたこと（発生と復旧の時刻・影響の範囲）→ 現在の状態 → 相手に判断を求める事項 → 経過 → 原因 → 再発防止策（担当者と期限）。
- 依頼：依頼の内容・期限・理由を最初に書き、相手の判断に必要な材料を添える。
- 提案：決定を求める事項と期限 → 推奨案と理由 → 他の案 → 決定しない場合の影響。
- お知らせ：変更の内容と開始日 → 読み手の作業 → 例外 → 問い合わせ先。
- 詫び：詫び → 起きたこと → 原因 → 今後の対応。言い訳を先に書かない。
- 断り：クッション言葉 → 結論（断る）→ 理由（短く）→ 代替案。結論は明確に書き、断定の強さは相手との関係で選ぶ。長い付き合いの相手には「お受けできません」より「〜は難しい状況です」と書き、直後に代替案を続けて、断りであることが伝わるようにする。
- 催促：前の依頼（日付と件名）→ 未着であること → 新しい期限。相手を責める言葉を使わない。
- 手順書：1ステップに1操作。条件つきの手順は場面ごとに分ける。手順の番号と図の番号をそろえる。警告は「**注意**」のように強調してよい。
- 議事録：決定事項・未決の事項・担当者と期限のある課題を先に書き、経緯は後ろに書く。社外に送る議事録も、話した順ではなくこの順にし、文体は です・ます、相手の会社の人には「様」を付ける。
  - 書くのは会議で言われたことだけにする。誰も言っていない担当・期限・約束（「日程は先方からご連絡いただきます」「当社から回答します」）は、要ると思えば議事録に書かずに依頼者へ「〜を足しますか」と伝える。議事録は後で言った・言わないの拠り所になり、足した一文が約束として読まれるため。やることは出たが担当や期限が決まらなかった件は、課題の欄に「担当・期限は未定」と書いて残す。
  - 決まらなかった件も、未決の事項として本文に残す。配布先に合わないかもしれないと思っても、残したまま依頼者に「外しますか」と聞く。先に削ると、依頼者が気づかなければその件がどこにも残らないため。外すのは、「書かないで」と言われた発言と、社外に送る議事録での自社の内側の話（相手が退室したあとの話、自社の値付けの判断）で、外したことを依頼者に伝える。
  - 社外に送る議事録では、相手の社内の事情や本音の発言（「うちの部長は正直乗り気じゃない」）をそのまま引かず、議題としての要点（「社内でのご検討の状況を確認」）に言い換える。相手は自分の言葉が記録に残って社内に回るのを望まないことが多いため。

## 作業報告の例

変更の記録から書いた作業報告を、SKILL.md の「文章の形」で直した例。

直す前：

```
- **ブラウザ操作（#104、11/9）**：Web ページを開く・読む・入力する作業の手順。手段の選び方と、ログインや取り消せない操作の扱いを決めた。
- **ツールの版の見張り（#77）**：入っている道具の版を最新と比べる道具を足した。見るだけで、更新はしない。
```

直した後：

```
11月9日に、Web ブラウザを操作する手順を追加しました。ページを開く手段を選ぶ順序と、ログインや取り消せない操作の扱いを定めています。

また、導入済みのツールの版を最新版と比較するツールを追加しました。このツールは版の遅れを通知します。ただし、更新は行わないため、利用者が更新します。
```
