# 日本語の文章を書く・修正する

会社・リポジトリ・文書に文章の規則（文体ガイド、用語集、表記の統一表）がある場合は先に読んで従う。この Skill は、規則が無い部分の既定を定める。

手順の重さは文章の規模で変える。チャットや数行の返信には、「読み手から書く」の1〜3と「書いたあとに確認する」を適用する。保存される文書と配布する文書（報告・お知らせ・手順書・提案・docs）には全体を適用し、検査スクリプトを実行し、公開の前に文脈を持たない読み手に読ませる（`cold-read` があれば使う）。

## 読み手から書く

1. **読み手を一人に決める。** 誰が、どの場面で、何のために読むか。何を知らないか。宛先が多い場合は、最も多い読み手か、最も困る読み手を選ぶ。
2. **最初の文で、何についての文書かを書く。** 対象が何であるか、または何が起きたかを書く（「check.mjs は日本語の文章を検査するスクリプトです。」「11月に24件の変更を取り込みました。」）。手元の事実をすべては載せない。書けない場合は、調べるか質問する。
3. **読み手への依頼がある場合は、対象を示した直後に、読み手の動作で書く。** 「仕様が変わりました」で終えず、「〇日までに設定を見直してください」まで書く。依頼が無い文書（報告・解説）には、依頼が無いことを書かない。指示・制限・例外には理由を隣に書く。理由が材料に無い場合は、依頼者に質問するか、不明と伝える。書き手の事情（経緯・苦労）は後ろに回す。
4. **読み手がその場面で使う言葉を選ぶ。** 書き手の作業の言葉（コードの名前、社内の管理番号、その場で作った呼び名）は使わない。読み手が使う番号（注文番号）は書く。
5. **題名・件名・見出しには、読み手の場面か問い、または結論を書く。** 「概要」「その他」「〇〇について」で済ませない（「売上の推移」→「売上は3か月続けて伸びている」）。問いの見出しの下は答えから書く。動詞の見出しには目的語を付ける（「動かす」→「スクリプトを実行する」）。

「それ何？」（読み手の知らない言葉）と「だから何？」（読み手にとっての意味が無い）は読み手にしか見つけられない。

## 場面で決める

同じ内容でも、相手・媒体・文書の種類で書き方は変わる。伝わり方には「正確さ」「分かりやすさ」「ふさわしさ」「敬意と親しさ」の4つがあり、互いに衝突する。どれを優先するかを場面ごとに決める。

書く前に次を決める。場面ごとの既定は [references/business.md](references/business.md) の「場面ごとの既定」の表にある。

- 文体（です・ます か である か）。見出し・箇条書き・表は本文と別に決めてよい。
- 相手との距離。敬語の重さ・挨拶・クッション言葉で調整する。社外は重く、社内は軽く、チャットはさらに軽くする。軽くしても敬語は省かない。
- 順番。結論を先に書くことを既定とする。詫び・断りはクッション言葉と詫びを先に、記事は読み手の場面を先に置いてよい。
- 往復できるか。チャットとメールの返信は短くてよい。お知らせ・手順書・議事録・依頼は、読み手が問い合わせずに済むよう、1回ですべて書く（いつ・誰が・何を・どこで・期限・問い合わせ先）。
- 専門用語の扱い。読み手の前提知識に応じて、言い換える、説明を添える、そのまま使う、のいずれかを選ぶ。
- 見出し・箇条書き・表の量。手順書・議事録・稟議・スライドは多く、依頼のメール・記事・詫びは文章でつなぐ。
- 表示される場所。メール・チャット・Word・PowerPoint では Markdown の記号（`##`・`**`）がそのまま表示されるため、見出しは「■」や【】で示す。
- 長さ。内容で決める。読み手が問い合わせや再調査をすることになる短さは短すぎる。

## 文章の形

AI が書く日本語は次の9点で不自然になる。書くときと確認するときに最初に見る。

1. **細かく区切らない。** 説明・理由・経緯は段落の文章で書く。箇条書きは、並列の項目（3つ以上）と手順に使う。1つの項目が2文以上になる場合は段落に戻す。「**名前**：説明」の形で項目を立てない。読点が4つ以上の文は、語順を変えて減らす（「ファイルごとに、件数と、一覧が出ます」→「件数と一覧がファイルごとに出ます」）。短い文に読点を打たない。読点の後ろが12字以下で文が終わる場合は、読点を省くか、前後の文とつなぐ（「出力された箇所は、修正の候補です。」→「出力された箇所は修正の候補です。」）。
2. **文と文をつなぐ。** 前の文との関係を文頭の接続詞で示す。追加は「また」、補足は「なお」、逆接は「しかし」「ただし」、因果は「そのため」「このため」を使う。目安として、人が書く報告と解説は10文に1文が接続詞で始まる。理由は「〜します。〜のためです。」と後ろの文に分けず、「〜のため、〜します」と1文で書く。前の文は「これは」「その結果」で受ける。短い文が3つ続く場合は1文にまとめる。逆接でない「が、」と、「〜は仕様で、」のような「で、」では文をつながない。「〜であり、」とするか、文を分ける。
3. **括弧で補足しない。** 用語の説明は本文に1回書く。読み手に不要な補足は削除する。留保を括弧に入れない。曜日・税込・略語の正式名・定義・参照先（「別紙1参照」）の括弧は使ってよい。
4. **述語から主語と目的語を確認する。** 述語の「誰が」「何を」が、その文か直前の文にあることを確認する（「修正するときは」→「指摘された文を修正するときは」）。動作の主体が変わる箇所では主体を書く。目的語は「を」で書き、「〜は、」で文頭に出さない（「PDF の読み取りは、11月6日に手順を追加しました」→「11月6日に、PDF を読み取る手順を追加しました」）。段落の書き出しを「〜は、」でそろえない。範囲は「〜では」、時点は日付、前の段落との関係は接続詞か「この〜」で始める。仕組みの動作や規則のように主体が読み手に不要な場合は、受け身で書く（「設定は毎朝6時に更新されます」）。主語の無い能動文（「更新はしない。」）は書かない。「同じ」「別の」は、何と比べているかを書く（「同じフォルダーに」→「check.mjs と同じフォルダーに」）。
5. **同じ物は同じ語で呼び、同じ内容を2回書かない。** 新しい情報の無い文は削除する。事実を書いた後に、同じ内容を指示の形で繰り返さない。並列の項目は1つの列挙にまとめ、「〜も同じです」と後から追加しない。
6. **否定・対比・留保から書き始めない。** 伝える内容を肯定の形で先に書く（「ツールは文章を修正しません。修正するのは人です。」→「修正するかどうかは、ツールが出力した一覧を見て利用者が判断します。」）。しないこと・できないことは、読み手が誤解しやすい場合に、後ろに1回書く。「〜ても」の譲歩の前に、元になる事実を書く（「件数が多くても終了コード 0 を返します」の前に「読めた場合は 0 を返します」）。
7. **「〜のは〜です」の形で書かない。** 英語の強調構文の直訳であり、続くと翻訳調になる。主語を示し、動詞で言い切る（「この検査で分かるのは書き方の癖だけです。」→「この検査は書き方の癖を検出します。」）。
8. **文書の語彙で書く。** 説明資料・報告・手順書には、話し言葉と幼い言い回しを使わない（動かす→実行する、直す→修正する、見るところ→確認箇所、当たる→該当する、わざと→意図的に、次は→以下は）。理由は「〜ので」より「〜ため」、限定は必要な箇所にとどめ、書く場合は「〜だけ」より「〜のみ」を使う。必要な条件は「〜には〜が必要です」と書く（「Node.js が入っていれば動きます」→「検査スクリプトの実行には Node.js が必要です」）。補足の情報は「〜こともできます」と書く。和語の動詞を名詞にしない（「結果の確かめ」→「結果の確認」）。チャットと記事は話し言葉に寄せてよい。
9. **抽象的な言い方を避け、対象と動作を書く。** 方向・比喩・「〜で決まります」で説明しない（「迷うものは残さない側に倒します」→「採否を判断できない項目は除外します」）。出力の形式は文で説明せず、形式そのもの（「行番号: [種類] 説明」）を1行で示す。この Skill の指示を本文に書かない（「結論から書きます。」と宣言せず、結論を書く）。

例（変更の記録から書いた作業報告）。

直す前：

```
- **ブラウザ操作（#104、11/9）**：Web ページを開く・読む・入力する作業の手順。手段の選び方と、ログインや取り消せない操作の扱いを決めた。
- **ツールの版の見張り（#77）**：入っている道具の版を最新と比べる道具を足した。見るだけで、更新はしない。
```

直した後：

```
11月9日に、Web ブラウザを操作する手順を追加しました。ページを開く手段を選ぶ順序と、ログインや取り消せない操作の扱いを定めています。

また、導入済みのツールの版を最新版と比較するツールを追加しました。このツールは版の遅れを通知します。ただし、更新は行わないため、利用者が更新します。
```

## 書くときの判断

1. **断定の強さは根拠で決める。** 確認した事実は断定する。確認していないことは推測と明記し、根拠か、不明な点を添える。「かもしれません」を重ねない。提案・所見・記事では、「〜と考えます」「〜を勧めます」と書き手の判断を書く。
2. **材料の事実を拡大も縮小もしない。** 範囲・数・時点の異なる事実を1つにまとめない（「全顧客に影響」と「その時間にログインを試みた約300社」から「すべてのお客様がログインできませんでした」と書かない）。
3. **名詞を連ねない。** 「支援金支給の実施」より「支援金を支払います」。名詞が3つ以上続く場合は動詞を使う。
4. **前置きを書かない。** 「以下で説明します」を書かず、結論から書く。メールの挨拶、クッション言葉（「恐れ入りますが」）、相手の手間への一言（「お忙しいところ」）は残す。
5. **定型の表現をそのまま使う。** 業務の定型（「お世話になっております」「ご確認ください」）は言い換えない。比喩、誇張（「劇的に」）、擬人化（「データが語る」）を使わない。
6. **人も物も悪く書かない。** 他部署・前任者・製品は起きた事実で書く。
7. **変わる可能性のある事実には時点を書く。** 版・価格・体制・予定は「2026年11月時点で」と書く。

業務の文書には、[references/business.md](references/business.md) の文体・敬語・表記・数字と日付・文書の型も適用する。

## 削りすぎない

簡潔にすることと、必要な情報を削ることは異なる。次の4つは削らない。

- 読み手の行動を変える理由と、条件・範囲・主体を示す語。
- 論理を示す接続の言葉。
- 敬語の定型（挨拶・結び・詫び・依頼・クッション言葉）と、相手への一言（感謝・手間への詫び）。
- 読み手が問い合わせることになる情報（期限・場所・問い合わせ先・次の作業）。

## AI に書かせるとき

依頼者が渡す情報（読み手・目的・伝える1文・場面・見本）は [references/asking-ai.md](references/asking-ai.md) にある。Skill を使えない相手には、「読み手から書く」「文章の形」「書いたあとに確認する」を依頼文に貼る。

## 書いたあとに確認する

1. 読み手が最初の数行で、何についての文書かと、自分への依頼の有無を理解できるか。知らない言葉が無いか（それ何？）。読み手にとっての意味が書いてあるか（だから何？）。
2. 場面に合っているか。社外の文書が軽すぎないか、チャットが重すぎないか。敬語が不足して冷たくなっていないか、過剰でよそよそしくなっていないか。
3. 「文章の形」の9点。通読では見落とすため、段落ごとに確認する。
4. 指示・制限・例外の文ごとに、理由が隣にあるか。
5. 同じ事実を2か所に書いていないか。どの文書にも当てはまる一般論（「〇〇は重要です」）と、内容を示さずに注意を促す文（「ここがポイントです」）は削除する。判断できない文は残す。文末を変える目的で、体言止め・問いかけ・常体を混ぜない。文末の連続は、2文をつなぐか主語を入れ替えて解消する。

## 検査スクリプトで確認する

```
node "<この Skill のフォルダー>/scripts/check.mjs" "<文章のファイル>" [--article] [--max-length 100]
```

- `<この Skill のフォルダー>` はこの SKILL.md があるフォルダーである（例：`~/.claude/skills/japanese-writing`、`~/.agents/skills/japanese-writing`）。パスは引用符で囲む。
- 入力は UTF-8 のテキスト（.md・.txt）である。Word・PowerPoint・メール・チャットの文は、一時フォルダー（Windows では `%TEMP%`）に UTF-8 のテキストとして保存してから渡す。UTF-8 以外のファイル（Shift_JIS、PowerShell 5.1 の `>` で出力した UTF-16）は、文字化けとして終了コード 1 で停止する。
- 確認箇所を、行番号と種類を付けて出力する。既定の種類は `repeat`・`hidden`・`tone`・`style`・`keigo`・`kana`・`format`・`shape`（文章の形）である。記事・ブログ・README の説明文には `--article` を付ける。文の長さと文末の単調さ（`flat`・`ending`）と AI の文に多い語（`aiword`）も検査する。種類ごとの内容はスクリプト冒頭の注釈にある。
- 出力された箇所は修正の候補であり、修正するかどうかは文脈で判断する。件数を合否の基準にしない。正規表現による検査のため、問題の無い文が該当することがある。固有名詞・法令名・画面の言葉・引用・定型は表記が決まっているため、修正しない。
- 検査と修正の往復は2回までとし、残った箇所は残す。言い換える場合は元より具体的な語を選ぶ。修正すると事実・数字・理由が欠ける場合は修正しない。
- 0 件でも読み手に伝わるとは限らないため、「書いたあとに確認する」は省かない。

## 文章を修正するとき

- 意味の分かりにくい文は、「どういう意味？」と質問された場合の答えに書き換える。
- 人から受けた指摘は、その1か所の修正方法でなく、例として受け取る。同じ観点で文書全体を確認する。その情報が必要か、読み手と場面に合うかまで戻って確認する。
- 事実・数字・固有名詞・引用・画面の言葉・本人が書いた段落（体験・意見）は変更しない。修正後に、意味・条件・断定の強さが変わっていないことを確認する。
