# 日本語の文章を書く・修正する

会社・リポジトリ・文書に文章の規則（文体ガイド、用語集、表記の統一表）がある場合は先に読んで従う。この Skill は、規則が無い部分の既定を定める。

手順の重さは文章の規模で変える。チャットや数行の返信には、「読み手から書く」の1〜3と「書いたあとに確認する」を適用する。保存される文書と配布する文書（報告・お知らせ・手順書・提案・docs）には全体を適用し、検査スクリプトを実行し、公開の前に、書いた経緯を知らない読み手に読ませる。

## 読み手から書く

1. **読み手を一人に決める。** 誰が、どの場面で、何のために読むか。何を知らないか。宛先が多い場合は、最も多い読み手か、最も困る読み手を選ぶ。
2. **最初の文で、何についての文書かを書く。** 対象が何であるか、または何が起きたかを書く（「check.mjs は日本語の文章を検査するスクリプトです。」「11月に24件の変更を取り込みました。」）。手元の事実をすべては載せない。書けない場合は、調べるか質問する。
3. **読み手への依頼がある場合は、対象を示した直後に、読み手の動作で書く。** 「仕様が変わりました」で終えず、「〇日までに設定を見直してください」まで書く。依頼が無い文書（報告・解説）には、依頼が無いことを書かない。指示・制限・例外には理由を隣に書く。理由が材料に無い場合は、依頼者に質問するか、不明と伝える。書き手の事情（経緯・苦労）は後ろに回す。
4. **読み手がその場面で使う言葉を選ぶ。** 書き手の作業の言葉（コードの名前、社内の管理番号、その場で作った呼び名）は使わない。読み手が使う番号（注文番号）は書く。
5. **題名・件名・見出しには、読み手の場面か問い、または結論を書く。** 「概要」「その他」「〇〇について」で済ませない（「売上の推移」→「売上は3か月続けて伸びている」）。問いの見出しの下は答えから書く。動詞の見出しには目的語を付ける（「動かす」→「スクリプトを実行する」）。

## 場面で決める

同じ内容でも、相手・媒体・文書の種類で書き方は変わる。まず、読まれ方を次から決める。腰を据えて通読する（報告・解説）、探して拾い読みする（手順書・FAQ）、通りがかりに数秒で見る（掲示・注意書き・画面の文言）、会話の流れで読む（チャット）。数秒で見るものは、してほしい行動を最初に短く並べ、理由は1行で添え、経緯は省くか末尾に置く。会話の流れで読むものは、用件を数文にとどめ、詳しい内容は置き場所を示す。

次も決める。場面ごとの既定は [references/business.md](references/business.md) の「場面ごとの既定」の表にある。

- 文体（です・ます か である か）。見出し・箇条書き・表は本文と別に決めてよい。
- 相手との距離。敬語の重さ・挨拶・クッション言葉で調整する。社外は重く、社内は軽く、チャットはさらに軽くする。軽くしても敬語は省かない。
- 順番。結論を先に書くことを既定とする。詫び・断りはクッション言葉と詫びを先に、記事は読み手の場面を先に置いてよい。
- 往復できるか。チャットとメールの返信は短くてよい。お知らせ・手順書・議事録・依頼は、読み手が問い合わせずに済むよう、1回ですべて書く（いつ・誰が・何を・どこで・期限・問い合わせ先）。
- 専門用語の扱い。読み手の前提知識に応じて、言い換える、説明を添える、そのまま使う、のいずれかを選ぶ。
- 見出し・箇条書き・表の量。手順書・議事録・稟議・スライドは多く、依頼のメール・記事・詫びは文章でつなぐ（並列の項目は「文章の形」の1）。
- 表示される場所。メール・チャット・Word・PowerPoint では Markdown の記号（`##`・`**`）がそのまま表示されるため、見出しは「■」や【】で示す。
- 長さ。内容で決める。読み手が問い合わせや再調査をすることになる短さは短すぎる。

## 文章の形

読み手は書き手に聞き返せない。次の9点は、通読する文書で、読み手が「何の話か」「前の文とどうつながるか」「結局何が言いたいか」「自分に向けた言葉か」を聞き返したくなる典型で、AI の文に多い。書くときと確認するときに最初に見る。9点に無い形でも、この問いに答えられていない文は修正する。

9点の言葉に当たっても、その場面の読み手が困らない箇所は変更しない。手順・連絡先・並列の項目は一覧のまま残す。数秒で見る掲示は、体言止めと箇条書きで書いてよい。

1. **細かく区切らない。** 説明・理由・経緯は段落の文章で書く。箇条書きは並列の項目（3つ以上）と手順に使い、1つが数文になっても箇条書きか小見出しで分け、中の文はつなぐ。目印の無い「1つ目は…」の段落や、「次の3つです。A、B、Cです。」の1文に詰めない。「**名前**：説明」の形で項目を立てない。読点が4つ以上の文は、語順を変えて減らす（「ファイルごとに、件数と、一覧が出ます」→「件数と一覧がファイルごとに出ます」）。読点の後ろが12字以下で文が終わる場合は、読点を省くか、前後の文とつなぐ（「出力された箇所は、修正の候補です。」→「出力された箇所は修正の候補です。」）。
2. **文と文をつなぐ。** 前の文との関係を文頭の接続詞で示す。追加は「また」、補足は「なお」、逆接は「しかし」「ただし」、因果は「そのため」「このため」を使う。接続詞は、前後の関係を読み手が補えない箇所に置く。同じ主題が続く文には不要である。理由は「〜のため、〜します」と前に置く。「〜します。〜のためです。」と後ろの文に置く形は、結論が既に文脈にある場合と、禁止や指示を先に伝える場合に使う。逆接でない「が、」と、「〜は仕様で、」のような「で、」では文をつながない。「〜であり、」とするか、文を分ける。
3. **括弧で補足しない。** 用語の説明は本文に1回書く。留保を括弧に入れない。曜日・税込・略語の正式名・定義・参照先（「別紙1参照」）・確認の印の括弧は使ってよい。
4. **述語から主語と目的語を確認する。** 述語の「誰が」「何を」が、その文か直前の文にあることを確認する（「修正するときは」→「指摘された文を修正するときは」）。動作の主体が変わる箇所では主体を書く。目的語は「を」で書き、「〜は、」で文頭に出さない（「PDF の読み取りは、11月6日に手順を追加しました」→「11月6日に、PDF を読み取る手順を追加しました」）。主題（「〜は」）は次の文にもかかるため、同じ主題は毎文に書かない。前の文に出た物を次の文の主題にしてつなぐ。段落の書き出しを「〜は、」でそろえない。範囲は「〜では」、時点は日付、前の段落との関係は接続詞か「この〜」で始める。仕組みの動作や規則のように主体が読み手に不要な場合は、受け身で書く（「設定は毎朝6時に更新されます」）。主語の無い能動文（「更新はしない。」）は書かない。「同じ」「別の」は、何と比べているかを書く（「同じフォルダーに」→「check.mjs と同じフォルダーに」）。見出しと名詞句も、何についてかを書く（「読み方」→「帳票の Excel の読み方」）。
5. **同じ物は同じ語で呼び、同じ内容を2回書かない。** 新しい情報の無い文は削除する。事実を書いた後に、同じ内容を指示の形で繰り返さない。並列の項目は1つの列挙にまとめ、「〜も同じです」と後から追加しない。
6. **否定・対比・留保から書き始めない。** 伝える内容を肯定の形で先に書く（「ツールは文章を修正しません。修正するのは人です。」→「修正するかどうかは、ツールが出力した一覧を見て利用者が判断します。」）。しないこと・できないことは、読み手が誤解しやすい場合に、後ろに1回書く。「〜ても」の譲歩の前に、元になる事実を書く（「件数が多くても終了コード 0 を返します」の前に「読めた場合は 0 を返します」）。
7. **「〜のは〜です」の形で書かない。** 英語の強調構文の直訳であり、続くと翻訳調になる。主語を示し、動詞の文にする（「この検査で分かるのは書き方の癖だけです。」→「この検査は書き方の癖を検出します。」）。
8. **文書の語彙で書く。** 説明資料・報告・手順書には、話し言葉と幼い言い回しを使わない（動かす→実行する、直す→修正する、当たる→該当する）。理由は「〜ので」より「〜ため」、限定は必要な箇所にとどめ、書く場合は「〜だけ」より「〜のみ」を使う。必要な条件は「〜には〜が必要です」と書く（「Node.js が入っていれば動きます」→「検査スクリプトの実行には Node.js が必要です」）。和語の動詞を名詞にしない（「結果の確かめ」→「結果の確認」）。チャットと記事は話し言葉に寄せてよい。
9. **抽象的な言い方を避け、対象と動作を書く。** 方向・比喩・「〜で決まります」で説明しない（「迷うものは残さない側に倒します」→「採否を判断できない項目は除外します」）。出力の形式は文で説明せず、形式そのもの（「行番号: [種類] 説明」）を1行で示す。この Skill の指示を本文に書かない（「結論から書きます。」と宣言せず、結論を書く）。

修正の前後の例は [references/business.md](references/business.md) の「作業報告の例」にある。

## 書くときの判断

1. **言い切るのは、確かめた事実だけにする。** 測った数字・試した結果・確かめた仕様は言い切る。確かめていないことは推測と明記し、根拠か不明な点を添える。読み手の受け取り方（伝わる・迷わない）や効果の見込み（楽になる）も所感のため和らげる（「伝わります」→「伝わりやすくなります」）。推測・意見の同じ文末が近くで続く場合は、[references/endings.md](references/endings.md) の選択肢で言い回しをずらす。確からしさを変えず、断定・推量・伝聞は入れ替えない。題名・見出し・最初の文も、本文と同じ強さで書く（本文に「広告のみの効果かは確認していません」と書くなら、題名で「広告で来店が増えた」と言い切らず、「広告を出した週に、来店が 120 人から 150 人になった」と起きたことを書く）。提案・所見・記事では「〜と考えます」「〜を勧めます」と書き手の判断を書く。
2. **材料の事実を拡大も縮小もせず、材料に無いことを足さない。** 見込み・勧め・今後の予定・相手への約束・理由・決まりは、材料に無ければ書かない。話の筋に必要な場合は、本文の中に「（要確認）」と印を付け、依頼者に確認する。範囲・数・時点の異なる事実を1つにまとめない（「全顧客に影響」と「その時間にログインを試みた約300社」から「すべてのお客様がログインできませんでした」と書かない）。
3. **名詞を連ねない。** 「支援金支給の実施」より「支援金を支払います」。名詞が3つ以上続く場合は動詞を使う。
4. **前置きを書かない。** 「以下で説明します」を書かず、結論から書く。メールの挨拶、クッション言葉（「恐れ入りますが」）、相手の手間への一言（「お忙しいところ」）は残す。
5. **定型の表現をそのまま使う。** 業務の定型（「お世話になっております」「ご確認ください」）は言い換えない。比喩、誇張（「劇的に」）、擬人化（「データが語る」）を使わない。
6. **人も物も悪く書かない。** 他部署・前任者・製品は起きた事実で書く。
7. **変わる可能性のある事実には時点を書く。** 版・価格・体制・予定は「2026年11月時点で」と書く。

業務の文書には、[references/business.md](references/business.md) の文体・敬語・表記・数字と日付・文書の型も適用する。

## 削りすぎない

- 読み手の行動を変える理由と、条件・範囲・主体・期限・問い合わせ先・次の作業を示す語。
- 論理を示す接続の言葉。
- 敬語の定型（挨拶・結び・詫び・依頼・クッション言葉）と、相手への一言（感謝・手間への詫び）。

## 書いたあとに確認する

1. 読み手が最初の数行で、何についての文書かと、自分への依頼の有無を理解できるか。知らない言葉が無いか（それ何？）。読み手にとっての意味が書いてあるか（だから何？）。
2. 場面に合っているか。社外の文書が軽すぎないか、チャットが重すぎないか。敬語が不足も過剰もしていないか。
3. 「文章の形」の9点と、その前の4つの問い。通読では見落とすため、段落ごとに確認する。読み手が困らない箇所まで変更していないか。
4. 指示・制限・例外の文ごとに、理由が隣にあるか。
5. 同じ事実を2か所に書いていないか。どの文書にも当てはまる一般論（「〇〇は重要です」）と、内容を示さずに注意を促す文（「ここがポイントです」）は削除する。判断できない文は残す。文末の連続は、2文をつなぐ、主語を入れ替える、言い回しをずらす、で解消する。文末を変える目的で、問いかけ・常体を混ぜない。文末を変える目的の体言止めは、記事・エッセイの短い文に限る。

## 検査スクリプトで確認する

```
node "<この Skill のフォルダー>/scripts/check.mjs" "<文章のファイル>" [--article] [--max-length 100]
```

記事・README の説明文には `--article` を付ける。入力の作り方と検査の種類は [references/check.md](references/check.md) にある。出力された箇所は修正の候補であり、文脈で判断する。検査と修正の往復は2回までとする。0 件でも「書いたあとに確認する」は省かない。

## 文章を修正するとき

- 意味の分かりにくい文は、「どういう意味？」と質問された場合の答えに書き換える。
- 人から受けた指摘は、その1か所の修正方法でなく、例として受け取る。同じ観点で文書全体を確認する。その情報が必要か、読み手と場面に合うかまで戻って確認する。
- 事実・数字・固有名詞・引用・画面の言葉・本人が書いた段落（体験・意見）は変更しない。本人の意見の文末（「〜と思います」）と言い回しも、この Skill の規則（文書の語彙・文末をずらす手順）に合わせて書き換えない。修正後に、意味・条件・断定の強さが変わっていないことを確認する。
- 他人の下書きでは、前の話を踏まえて読める順か（困りごとの前にやり方が来ていないか）を見る。直す前に、読み手が知らない語（道具の名前・機能の名前・社内の呼び名）を書き出し、題名・見出しを含めて初めて出る所で、元の語を残して1文で説明する（「ピボットテーブル」→「表を項目ごとに集計し直す Excel の機能（ピボットテーブル）」）。同じ物の2つの呼び名は1つにそろえる。
