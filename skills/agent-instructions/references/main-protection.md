# main の守り方（GitHub）

リポジトリを作るとき・守りを見直すときに読む。GitHub の ruleset と必須の CI の作り方と落とし穴。GitLab などほかの置き場では、同じ考え（PR 必須・必須の検査・例外を置かない）を、その置き場の保護の設定で作る。

エージェントに「CI を待ってからマージ」と書くだけでは、急いだとき・複数のエージェントが並行したときに破られる。GitHub の ruleset で main を機械的に守る。

- 入れるもの：PR 必須（承認の数は0でよい）、必須の CI、force push と削除の禁止、マージの方法を実際に使うものに絞る。
- 例外（bypass）は置かない（自分自身も含む）。個人アカウントのリポジトリでは GitHub Actions を例外にできない。bot が定期的にコミットする仕組み（記録の積み上げなど）は、main ではなく専用のブランチに書かせる。
- 「ブランチを最新にしてからマージ」（strict）は、リポジトリの変更頻度と検証のしかたで決める。付けると、並行した変更がまとまったあとに main が壊れるのを防げる（GitHub も明記するトレードオフ）。代わりに、並行してマージするたびに CI のやり直しになり、費用と待ち時間が増える。main への push でも同じ検査を回しているなら付けない選択もある。main で検査しないリポジトリで並行したマージが多いなら、付けることを考える。
- 必須にする CI は、**どの PR でも必ず走って結果を返す job** にする。
  - workflow の `paths` / `paths-ignore` で走らなかった PR は報告が来ず、マージできなくなる。範囲の判定は job の中で行う。
  - 条件で skipped になった job を、GitHub は必須チェックの成功として扱う。同じコミットに後から来た skipped が、本物の失敗の上に重なって通ってしまう。draft や範囲外は、まとめ役の job（関門）が明示的に赤・緑を返す。
- 入れたら、効いていることを確かめる：`gh api repos/<owner>/<repo>/rules/branches/main`。bot の定期のコミットがあれば、手動で1回走らせて通ることも見る。
- CI そのものが壊れてマージできないときは、所有者が ruleset を一時的に Disabled にし、直したら必ず Active に戻す（`gh api repos/<owner>/<repo>/rulesets` の `enforcement` で確かめる）。手順をリポジトリの docs に書いておく。
