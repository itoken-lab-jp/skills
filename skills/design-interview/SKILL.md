# 設計のインタビュー

AI が大量の仕様書や設計書を作り、人が後からまとめて読んで承認する形は、読む量が判断できる量を超え、読まずに承認することになる。判断は設計の会話の中でユーザーが下し、文書はその記録にとどめる。記録は一緒に決めたことなので、書き上げた文書を改めて読ませて承認を求めない。

github.com/mattpocock/skills の `grilling`（`grill-me` の本体）の、前提が決まった問いを回ごとにまとめて聞く進め方を取り入れた。github.com/addyosmani/agent-skills の `interview-me` からは、一般論の答えを本当に欲しいものへ聞き返す考えを、github.com/obra/superpowers の `brainstorming` からは、頼みに全部書いてあれば聞かずに作る入口と、途中で大きくなったら一段上げる考えを取り入れた（どれも MIT。文は借りていない）。Anthropic も、大きめの機能では先に Claude にインタビューさせて仕様を書かせ、新しいセッションで実装することを勧めている（code.claude.com/docs/en/best-practices の Let Claude interview you。2026-10-23 に確認）。

リポジトリに設計の進め方（ADR、仕様のひな形、Issue の型）が定めてあれば、それに従う。ここは定めが無い所の既定。

## いつ使うか

- 大きめの新規の作業（新しいアプリ・機能・仕組み）と、大改修（作り替え、データの持ち方や境界を変える直し）を頼まれたとき。頼みが「いい感じに作って」の形でも、作り始める前にここから入る。
- 小さい直し、小さい新規（数ファイルで済む道具・部品）、やることが一つに決まっている作業には使わない。頼みに目的・範囲・完了の形が全部書いてあれば、大きめでも聞かずに作り、何を決めて作ったかを報告に書く。迷ったら、観点の一覧だけ見せて、詰めるかどうかを1回聞く。
- ユーザーが「決めて進めて」と言ったときは、観点の一覧のうち目的・範囲と、取り返しのつかない決定や後で変えにくい決定（データの持ち方、境界、外部との約束）だけを1回で聞き、ほかは決めて進めて記録に残す。

## 進め方

1. **観点の一覧を出す。** 下の土台の一覧から、この案件で決める必要があるものを選び、足りない観点を理由つきで足す。各観点に、分かっている所と、決めることを1行ずつ書く。会話・リポジトリ・Issue から分かる事実は、一覧を出す前に調べて埋め、ユーザーには聞かない（調べる量が多ければ、サブエージェントに任せてよい）。調べきれなかった所は、推測で埋めずに「未確認」と書く。
2. **回に分けて決める。** 最初の回には、資料から読めても、目的と成功の基準（誰の何が、どうなれば成功か。できれば数で。例：「問い合わせへの最初の返事が、今の1日から1時間以内になれば成功、で合っていますか」）と、使う人と使い方を確かめる問いを必ず入れる（資料は作った人の想定で、今の困りごとと違うことがある）。大きな順は 目的 → 範囲と制約 → 中身（使い方・データ・つなぎ・守り・運用） → 受け入れの条件 → 進め方。1回に聞くのは、前提がもう決まっていて今答えられる問いすべてにし、まだ決まっていない答えに左右される問いは次の回に回す。答えで分かれた先の決定は、観点に枝として足す。ユーザーに聞くのは「何を・なぜ」（目的・範囲・優先）と、取り返しのつかない決定や後で変えにくい決定（データの持ち方、境界、外部との約束）。範囲から外すもの（「API 連携はやらない」など）も範囲の決定なので、黙って範囲外に置かず問いに入れる。合理的な既定のあるやり方（作る順、ファイルの分け方、ライブラリの細かい選択）は聞かずに決め、「決めた（既定）」として一覧に載せて、ユーザーが変えたければ変えられるようにする。問いには番号と、選択肢と推奨と理由を添え、「はい」で推奨を受け入れられる聞き方にする（選択肢で聞く道具があれば使う。Claude Code なら `AskUserQuestion`）。変えにくい決定の推奨には、その案で困る場面を最初から1つ添える。分かりきったことは聞かず、ユーザーが考えていなさそうな難所（境目の場合、失敗のしかた、引き換えにするもの）を掘る。答えが一般論（「拡張しやすく」「よくある形で」「〜すべきだと思う」）なら、そのまま決定にせず、「それで何ができると困らなくなるか」を使う場面1つで聞き返す。
3. **観点を閉じる。** 各観点を「決めた」「保留（いつ・何が分かれば決めるか）」「今回は決めない（理由1行）」のどれかにする。全部を埋めさせない。要らない観点は1行で閉じてよい。
4. **記録する。** 決めたこと、理由、捨てた案、保留の扱い、範囲外、触るファイルとつなぎ目（インターフェース）、受け入れの条件と端から端までの確かめ方を、回が終わるごとに足していく。決定の箇条で書く。置き場はリポジトリの定めに従う。定めが無ければ、次のセッションからも読める所にする：作業のブランチの docs の設計メモ（作業のブランチにコミットして push する）か、Issue のコメント（Issue の本文は書き換えない）。PR ができたら、本文から記録を指す。
5. **実装に入る。** 最後の回の終わりに「この記録で作り始めてよいか」を1問として足し、「はい」なら作り始める（要約を見せるためだけの往復を足さない）。受け入れの条件をテストに落としてから作る。決めた範囲の中のやり方は、聞かずに決めて進める。設計の会話が長くなって文脈が膨らんだら、記録を渡して新しいセッションで実装してよい。サブエージェントに任せるなら、下の「実装中に設計へ戻るとき」に当たったら自分で決めずに止まって報告するよう頼む（サブエージェントはユーザーと話せない）。終わりの報告には証拠（テストの出力、走らせたコマンドと結果、画面）を出す。人が見るのは、記録との差と証拠にする。

## 土台の一覧

- 目的：誰の何が困っていて、何ができたら成功か
- 範囲：やること、やらないこと
- 制約：期限、使える道具と契約、既存との互換
- 使う人と使い方の流れ
- データ：何を持つか、どこが正本か、移行
- 外とのつなぎ：外部のサービス、失敗したときの振る舞い
- 守り：権限、秘密、取り返しのつかない操作
- 運用：動いているのをどう見るか、壊れたらどう戻すか
- 受け入れの条件：テストや確かめの手順に落とせる形で
- 進め方：最初に作る最小のもの、区切り
- 大改修のとき：今の挙動のうち何を保つか、切り替えと戻し方

## 実装中に設計へ戻るとき

次のときは、黙って直さずに止まり、どの決定のどの前提が崩れたかと、直す案を出して、ユーザーと決め直す。決め直したら記録を直す。

- 決めた前提が事実と違った（外部の仕様、データの実物、性能）。
- 受け入れの条件を満たすには、決めた範囲・データの持ち方・境界を変えるしかない。
- 保留にした観点が、決めないと先へ進めなくなった。
- 小さいと見て、この手順を使わずに始めた作業が、作るうちに大改修の大きさになった（データの持ち方や境界に手が入る）。止まって、ここの「進め方」の1から始める。

決めた範囲の中で済むやり方の変更は、戻らずに進め、PR か記録に書く。
