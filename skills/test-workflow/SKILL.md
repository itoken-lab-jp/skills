# テストを書く・走らせる

エージェントの仕事は、通ったか落ちたかが分かる検査があって初めて閉じる。テストはその検査の中心で、速く・狭く・毎回同じ結果で回せるほど往復が減る。リポジトリの指示ファイル（AGENTS.md など）・README・CI の設定にテストのコマンドや分け方があれば、それに従う。

テストのための道具や依存（コンテナ・ブラウザの自動操作・テストのライブラリ）は、その PC で使えるかを、ユーザーの指示（その PC で毎回読まれる指示）で見る。無ければ自分で入れずにユーザーに伝える。リポジトリに依存を足すのは、リポジトリの定めに従う。

## 始めるとき

- 既存のリポジトリでは、変える前にテストを一度走らせる。走らせ方・件数・かかる時間と、もともと落ちているテストが分かる。走らせ方は指示ファイル・README・`package.json` などの scripts・CI の設定から探す。全部で長くかかるリポジトリでは、変える所に効く分だけにする。
- 共有の DB や本物の外部サービスに書き込むテストは、書き込み先がテスト用だと確かめられるまで走らせず、ユーザーに確かめる。件数を絞っても書き込みは防げない。
- もともと落ちているテストは、自分の変更のせいにも、黙って直す対象にもしない。落ちていたことを報告に書く。

## 書くとき

- 中身の作りではなく、外から見た振る舞いを確かめる。作り直してもテストが壊れない形にする。
- 新しく作るとき（TDD を頼まれたときも）は、テストを1つ足す → 落ちるのを見る → 通す、を繰り返す。テストを全部先に書いてから実装をまとめて書くと、作りながら分かったことがテストに返らない。どこを試すかは頼みと仕様から決め、それを聞くためだけには止まらない（作り始める前の確認が要る大きな作業は、その確認を先にする）。
- 期待する値は、実装と同じ計算で作らず、手で書いた値や仕様の例から取る。同じ計算で作った期待値は、実装が誤っていても通る。
- 不具合の直しや振る舞いの変更で足したテストは、直す前に赤になるのを見る。直したあとに書いたテストは、直す前でも通る（何も確かめていない）ことがある。
- 毎回同じ結果にする。時刻・乱数・ネット・並びの順は固定するか、テストの側で与える。揺れるテストは、通っても落ちても信用されなくなる。揺れたテストを、通るまで回し直して済ませない。揺れたことと、揺れの元（時刻・順番・共有の状態など）を報告する。
- 1つのテストで確かめる理由を1つにし、落ちたときの出力でどこが違うかが分かる書き方にする。

対象ごとの定石：

| 対象 | 試し方 |
|---|---|
| 計算・変換の関数 | 小さな単体のテストを多く書く。入力の幅が広いなら、組み合わせを手で並べる代わりに性質のテスト（JS の fast-check、Python の Hypothesis など）で乱数の入力を作る。落ちると道具が最小の例まで自動で縮めるので、その例を報告に出す。乱数の種は固定するか、落ちた種を出す |
| データの処理・SQL | 小さな入力ファイルと、期待する出力のファイルを並べて比べる |
| DB | 使えるならモックより本物の DB（コンテナなど）で試す |
| 外部の API | 記録した応答で試し、本物につなぐテストは少しにする |
| CLI・道具 | 実物を走らせ、終了コードと出力を確かめる |
| 画面・図 | 機械では、計算した位置・大きさ・表示する文字などの値を確かめる。見た目は撮って見る（下の「通ったあと」）。最後はユーザーの目 |

## 走らせ方（速さ）

- 作業中は、変えた所に効くテストだけを走らせる（例：`pytest path/test_x.py::test_name -x`、`node --test path/x.test.mjs`、`npx vitest run path/` や `npx vitest related --run <変えたファイル>`、`go test -run Name ./pkg`、`cargo test name`）。pytest の `--lf` は、前回の失敗が無いと全件を走らせる。全部は PR の前と CI で走らせる（上の、書き込み先を確かめられないテストは手元では除く）。
- 遅いテスト（多くの組み合わせを総当たりするもの、画面、外部につなぐもの）は、作業中の速いテストと分けておくと回しやすい。手元で走らせる範囲を減らすのは確かめる範囲を減らすことなので、分け方を変えるときはユーザーと決める。
- 1件が軽いテストに、pytest-xdist の `-n` を自分で付けない。ワーカーの起動の分だけ遅くなる（2026-11-14、Linux・4コア。1件が1ミリ秒ほどの500件で、時間1.5倍・CPU 3.9倍）。1件が重いテスト（DB・画面・外部につなぐもの）では並列が効くことがある（待つだけの1件0.1秒の40件で、時間0.4倍）ので、付けるなら前後で測る。リポジトリの設定にある並列は外さない。
- 確かめるだけの使い捨てのスクリプトで、重いライブラリを読み込まない（2026-10-30、クラウドの Linux で、Python の起動 約0.02秒に対し、pandas の読み込みは約0.5秒・約90MB）。集計・DB・Excel を読む専用の道具があれば、それを使う。

## 通ったあと

テストが通っても、思ったとおりに動くとは限らない。終える前に実物を動かして試す。

- CLI・関数：境目の入力で走らせてみる。
- Web の API：開発用のサーバーを立てて curl で叩く。終えたらサーバーを止める。
- 画面：ブラウザの自動操作（Playwright など、使えるなら）で撮って見る。デスクトップのアプリを画面操作で動かすなら、その手段の前提（ユーザーが PC の前にいて許可に答えられるときなど）に従う。
- 試して見つけた不具合は、赤になるテストにしてから直し、残す。

## テストを消させない

テストを消す・skip にする・mock に置き換える・期待を緩めるのは、仕様が変わったときだけ。エージェントは通すためにテストを消すことがある。

- PR では、テストのファイルの削除・skip の追加・mock への置き換え・期待の書き換え（スナップショットや期待する出力のファイルを一括で更新するのも含む）を差分で見て、理由が仕様の変更かを確かめる。レビューを頼むときは、この点を見る項目に入れる。
- 注意書きより仕組みで止める（テストを必須の CI にするなど）。ただし CI や main の守り（ruleset など）を変えるのは、頼まれたとき・リポジトリの守りを作る・見直すときにする。

## 出典

- Anthropic「Best practices for Claude Code」 https://code.claude.com/docs/en/best-practices ：通ったか落ちたかが分かる検査を持たせる、落ちるテストを書いてから直す、1ファイルだけ走らせるコマンドを CLAUDE.md に書いておく、言葉でなく走らせたコマンドと出力を証拠に出させる、終えたあと実際に動かして見る（`/verify`）。2026-10-31 に確認。
- Simon Willison「Red/green TDD」 https://simonwillison.net/guides/agentic-engineering-patterns/red-green-tdd/ ：実装の前にテストが落ちるのを確かめる。
- Simon Willison「First run the tests」 https://simonwillison.net/guides/agentic-engineering-patterns/first-run-the-tests/ ：既存のプロジェクトでは、まずテストを走らせる。
- Simon Willison「Agentic manual testing」 https://simonwillison.net/guides/agentic-engineering-patterns/agentic-manual-testing/ ：通っても動くとは限らない。`python -c`・curl・Playwright で試し、見つけた不具合はテストにして残す。
- Kent Beck（Pragmatic Engineer のインタビューの要約） https://newsletter.pragmaticengineer.com/p/tdd-ai-agents-and-coding-with-kent ：エージェントが通すためにテストを消す。
- 実測の数字は作者が測ったもの。`-n` は `tools/test-workflow/bench_xdist.py`（2026-11-14）、pandas の読み込みは 2026-10-30。そのほか（振る舞いを外から確かめる、毎回同じ結果、1つのテストに理由1つ、性質のテスト、期待する出力のファイルとの比較、本物の DB、記録した応答、揺れたテストを回し直さない、スナップショットの一括更新）は上の出典に無く、一般のやり方として足した。
