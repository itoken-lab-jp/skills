# Skill を作る

- **先にリポジトリの定めを読む**：作業するリポジトリの指示ファイル（AGENTS.md・CLAUDE.md など）と README に、Skill の置き場・配り方・試験の定めがあれば、そちらに従う。この Skill は、定めが無い項目の既定。
- **書式は公式で確かめる**：frontmatter の欄、name の形、description の長さは、使うツールの公式の docs と Agent Skills の仕様（agentskills.io/specification）で確かめる。確かめた数字は 2026-11-11 時点（下の「根拠」）で、ツールの版が上がったら確かめ直す。
- **Claude の skill-creator**：Claude には公式の skill-creator（Skill の下書きと評価の実行）もある。評価を回すのに使ってよいが、書き方の決まりは、この Skill とリポジトリの定めに従う（どのツールにも配る Skill を、Claude だけの形にしない）。
- **どこから読むか**：新しく作るときは 1 から順に。今ある Skill を直す・分けるときは 2 から。呼ばれない・呼ばれすぎる・従われないときは「4. 作ったあとに確かめる」の直し方から読む。

## 1. Skill にするか決める

- **Skill にする目安**：どれか1つに当たればよい。同じ手順を別の会話で2回説明したとき、同じ失敗が2回起きたとき、毎回は要らない知識が指示ファイルを長くしているとき。ユーザーが作ると決めたときは、それに従う。
- **Skill でない置き場**：どの作業でも毎回要ることは指示ファイルに、毎回必ず起きてほしいこと（編集後の整形、危ない操作を止める）はフックや CI に置く。Skill は呼ばれなければ効かない。Skill 以外に当たるときは、そう言ってユーザーと決める。
- **全体かリポジトリか**：どのリポジトリでも効くことは全体の Skill（ユーザーのホームの置き場）に、そのリポジトリでしか分からないことはリポジトリの Skill に置く。リポジトリの Skill のフォルダーはツールごとに違うので、使うツールの公式の docs で確かめる。
- **受け持ちを決める**：近い Skill がすでにあれば、足すより直すほうがよいかを先に見る。分けるときは、それぞれが何を受け持つかを決め、元の Skill には入口と分けた先の名前を残し、両方の description を「2. description を書く」の取り合いの項で直す。分けた・移したあとは、元の名前を指していた所（指示ファイル、ほかの Skill とその references）を検索し、移した先を指すように直す。
- **近い Skill は3か所で探す**：自分の Skill のほか、ツールに組み込みの Skill（Claude の pdf・xlsx など）と、作業するリポジトリの Skill。後の2つは見落としやすく、同じ頼みに両方が当たると、どちらに従うかがセッションごとに揺れる。全体の Skill とリポジトリの Skill が当たるなら、両方の description に、どちらが先かを書く（そのリポジトリの事情を持つ、狭いほうを先にする）。組み込みの Skill と当たるなら、こちらの description に「組み込みの〜がある環境でも、〜のときはこちらに従う」と書く。
- **使う場面を2〜3書き出す**：その Skill で済ませたい頼みを2〜3選び、それぞれをユーザーの言う言葉、手順、できあがりの形で書く。description の言葉と、「4. 作ったあとに確かめる」で出す頼みは、ここから取る。
- **先に1つ通す**：書く前に、その Skill が受け持つ頼みのうち難しいものを1つ選び、会話の中でユーザーが求める結果になるまでやる。実際の頼みがまだ無ければ、ユーザーに典型の頼みを1つ聞く。通ったやり方を抜き出して書く。抜き出すときは「3. 本文を書く」に合わせて書き直す（会話の中の一度きりの指図を、作業の間ずっと効く指示にする）。

## 2. description を書く

ツール（Claude Code・Codex など）は毎回、すべての Skill の name と description だけを読み、どれを開くかを決める。本文が正しくても、description で外れると効かない。

- **何をするかと、いつ使うか**の両方を書く。いつ使うかは、ユーザーが実際に言う言葉（「Excel を読む」「テストが遅い」）と、扱うファイルの種類・道具の名前で書く。作り手の側の言葉（中の関数名、設計の用語）だけで書かない。
- **いつ使うかは、頼みを受け取った時点で分かる言葉で書く。** Claude Code で試した範囲では、Skill が開かれたのは頼みを受け取ってすぐで、途中の節目（「報告する前に」「終える前に」）では開かれなかった。節目で効かせたい Skill も、「〜を頼まれたら、手を付ける前に読む」と頼みの種類で始め、節目でやることは本文に書く。頼みの種類で言えない中身（どの作業にも当たる確かめ）は、1 の「Skill でない置き場」に当たる。
- **「手を付ける前に読む」と書くのは、頼みの種類をはっきり言える Skill に絞る。** 同じ試しで、1回の頼みで開かれた Skill は多くが1本までで、強く書くと、同じ頼みに当たるほかの Skill（その作業の道具の Skill など）が読まれなくなった。両方を読ませたいときは、相手の description も頼みの種類で始める。
- **いちばん多い使い道と、それを呼ぶ言葉を先頭に置く。** 一覧には量の上限があり、Skill が多いと description は切られたり落とされたりする。Claude Code は1つあたり 1,536 字で切り、一覧が文脈の大きさの 1% を超えると、使うことの少ない Skill の description を丸ごと落とす（名前は残る）。Codex は一覧が文脈の 2% を超えると、まず description を短くし、それでも入らなければ Skill を一覧から外す。
- **全体の量を見る。** Skill を足したときと description を長くしたときは、一覧に入りきっているかを見る。Claude Code は `/context` の Skills の行と `/doctor` で見られる。入りきらないなら、使わない Skill を止めるか、description を短くする。
- **隣の Skill と取り合うとき**（どちらにも当たる頼みがあるとき）だけ、「〜には使わない」「〜は Skill 〜」と相手の名前を書く。取り合わないのに否定を並べると、description が長くなるだけ。
- **形を守る**：Agent Skills の仕様では、name は小文字・数字・ハイフンだけで 64 字まで、フォルダー名と同じにする。description は 1,024 字まで（全角も1字）。Claude（claude.ai・API）はさらに、frontmatter に `<` と `>` を使わないこと、name に anthropic・claude の文字を含めないことを求める。YAML として読めるよう、コロンのあとに空白を置く形（`: `）と、空白のあとの `#` を書かない（全角の「：」にする）。

## 3. 本文を書く

- **大事な手順と決まりを上に置く。** Claude Code は、会話が要約されたとき、呼んだ Skill の本文を先頭 5,000 トークンまでしか戻さない（呼んだ Skill が多いと、古いものは丸ごと戻らない）。本文がそれより長いと、後ろに置いた決まりは長い作業の途中で消える。
- **本文は 500 行未満、5,000 トークン未満を目安にする**（仕様の推奨。守れば、上の要約のあとも全文が戻る）。日本語は字数とトークンの比が決まらないので、リポジトリが字数の上限を試験にしていればそれに従い、無ければ Claude Code の `/context` で、Skill を呼ぶ前後の増え方を見る。呼ばれるたびに全文が入る。道具ごと・場合ごとの細部、長い例、作った経緯は `references/` に分け、本文から相対パスで指し、references から先へはつながない。references は開かれないことが多いので、外すと出来が変わる決まりは本文に置く。指すときは、何が書いてあるかと、いつ開くかを動作で書く（「業務の文書では、書き始める前に references/business.md を開く」。「〜にある」は開かれなかった）。
- **中身が、作った物を人に渡す前に確かめる問いの並びなら、短く書く。** AI がなぜ誤るかを1段落、問いを番号つきで並べ、説明は問いごとに1〜2文。見分け方の知識（ずれの形と原因の対応、数の目安）は残す。今ある Skill を縮めるときは、作るときに試した頼みでいまの版と比べてから置き換える。
- **言葉で守らせにくい検査は `scripts/` に置く。** 形の検証、数の突き合わせ、変換のように答えが1つに決まるものは、手順を文で書くよりスクリプトにして走らせるほうが確か。使う手順の横に、走らせるコマンドと依存（言語・道具）を書く。スクリプトの試験の置き場は、リポジトリの定めに従う。
- **作業の間ずっと効く指示として書く。** 本文は呼ばれたときに会話へ一度入り、後のターンでファイルを読み直さない。「テストを走らせる」より「編集のたびにテストを走らせる」と書く。
- **手順には、順と確かめと止め所を書く。** 段の順と、前の段から受け取るものを書く。各段で何を確かめてから次へ進むか、失敗したら何を戻して止めるかも書く。繰り返して良くする作業は、いつ止めるか（基準・回数）を書く。場合で道具を選ぶときは、選ぶ基準と、使えないときの代わりを書く。
- **例を入れる。** 典型の頼み1つを、ユーザーの言葉・やること・できあがりの短い例にする。
- **具体的に書く。** 「データを確かめる」ではなく、走らせるコマンドと、失敗したときによくある原因と直し方を書く。よく出るエラーは、出る文言・原因・直し方の組にする（長くなれば references/ へ）。
- 特定の PC にしか無い事情（入っている道具、パス、契約）は Skill に書かず、その PC で毎回読まれる指示ファイルや設定に置く。使える道具が PC で違うときは、「その PC の指示にある道具を使う」と書く。
- 出力に使う雛形（報告の型、テンプレートのファイル、画像）は `assets/` に置き、本文の使う所から指す。
- Skill のフォルダーの中に README.md を置かない。説明は SKILL.md と references/ に置く。

## 4. 作ったあとに確かめる

確かめの手間は、直した大きさに合わせる。Skill を新しく作ったときと本文を大きく書き直したときは、下を全部やる。description の言い回しや本文の数行の直しは、1（形）と、2 を使うはずの頼みの言い方1通りと、使わないはずの頼み1つだけにして進める（description を直すと、要らない頼みで呼ばれるようになることがある）（小さな直しのたびに全部を回すと、直す気が失せて古いまま残る）。

1. **形**：リポジトリの検査があれば走らせる。無ければ同梱の `node scripts/check-skills.mjs <フォルダー>`（パスはこの Skill から）を走らせ、Node が無ければ 2 の「形を守る」と公式の欄で照らす。
2. **呼ばれるか**：主に使うツール（複数に配るなら、いちばん使うもの）の新しいセッションで、その Skill を使うはずの頼みを言い方を変えて2〜3通り出し、全部で Skill が読まれるのを見る。使わないはずの、同じ言葉を含む別の頼みも1つ出し、読まれないのを見る。ほかの Skill も入った、ふだんの状態で試す（その Skill だけを置く試しや、必ず読ませる試しでは分からない）。「手を付ける前に読む」の形に直したら、同じ頼みに当たるほかの Skill が読まれているかも見る。書いた会話の続きでは試さない（書いたときの文脈が、本文の抜けを埋めてしまう）。自分で新しいセッションを開けないときは、ユーザーに頼むか、確かめていないと報告に書く。
3. **従われるか**：読まれたあと、本文の手順どおりに進むかを見る。読まれることと、意図どおりに動くことは別。同じ頼みを3回ほど出し、手順と出来が毎回そろうかも見る。references は開かれたかも見る（プロンプトに入れた試しでは分からない）。Skill が無いときとも比べる。比べる相手は、1 の「先に1つ通す」で Skill 無しで進めた会話の、聞き返しと手戻りの数。減っていなければ、Skill にした意味から見直す。比べていなければ、報告にそう書く。難しい頼みのほかに、罠の無い普通の頼みも1つ出し、Skill を入れて時間・道具の回数・人への問いが増えすぎていないかを見る（確かめや止まり所を書いた Skill は、普通の頼みまで重くすることがある）。
4. **合わないときの直し方**（直したら 2 からやり直す。2〜3回直して合わなければ、止めてユーザーに報告する）：
   - 呼ばれない：新しいセッションのエージェントに「Skill 〜はいつ使うか」と聞く。description をそのまま引いて答えるので、試した頼みの言葉のうち description に無いものが分かる。ユーザーの言い方とファイルの種類を足す。
   - 呼ばれすぎる：対象を狭く書くか、取り合う相手の Skill の名前を「〜には使わない」で書く。
   - 読まれても従われない：大事な決まりが後ろに埋もれているか、本文が長すぎるか、指示が曖昧か。上に移す、細部を references/ に出す、具体的に書き直す、決まった検査なら scripts/ にする。
5. 本文を大きく書いたときは、書いた文脈を持たない読み手（会話を引き継がず、指示ファイルも読まないサブエージェントなど）に読ませ、どこで迷ったかを聞いて直す。
6. **報告**：ユーザーには、何を確かめ（形・呼ばれるか・従われるか）、何を確かめていないかを書く。
7. **使い始めてから**：ユーザーが Skill の名前を出して呼ぶ、関係ない頼みで読まれる、途中で直されることが続く、のどれかが起きたら直す合図。そのときの頼みと起きたことを書き留め、4 の直し方で直す。Skill がいくつも増えたら、全部の description を並べて、同じ頼みに2つ以上当たるものと、中身が食い違うものを探す（足したときに見る「近い Skill は3か所で探す」を、全部について一度に）。

## 根拠

数字と決まりの出どころ（公式の docs と、自分で試した結果）と確かめた日は references/sources.md。数字を人に示すとき、ツールの版が上がって確かめ直すときに開く。
