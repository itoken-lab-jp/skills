# 仕事を任せる

任せた相手（子）は、この会話を見ていない。依頼文だけを読んで動き、報告だけを返す。任せる側の仕事は、依頼文で子の迷いを減らすことと、報告を実物で確かめることの2つ。道具ごとの起動のしかた（子の立て方、モデルの指定、道具の絞り方）は、使う道具の docs に従う。

## 1. 任せるかを決める

- **任せるのは3つだけ**：独立して並列にできる大きな仕事、読む量が多く結論だけが要る調べ物、自分の意図を渡さない別の目（欠陥を探すレビュー、文脈を持たない読み手）。線は「探す過程（検索の結果、ログ、外れのファイル）を自分の文脈に置く必要があるか」で引く。
- **任せないもの**：数回の操作で終わる仕事、計画づくり、途中の結果で後のやり方が変わる仕事、自分の作業の検算。要約の受け渡しで細部が落ち、途中の結果を見て計画を直せなくなる。分けるなら、作業の種類でなく文脈で分ける。
- **1体で足りるなら1体にする。** 同じ仕事を複数に割らない。並列にするのは筋が互いに依存しないときだけで、消費は本数分増える。
- **同じ形の仕事を多く割るときは、先に2〜3件だけ走らせる。** 試しで見つかった落とし穴（既定値の違い、検索に出ない書き方など）を依頼文に足してから残りに回す。いきなり全部を割ると、子ごとに違う直し方をして、まとめる側が全部を読み直すことになる。
- **並列の数は、返ってきたものを自分と人が読み切れる量までにする。** 読まずに受け取ると、確かめていないものを次の判断に使うことになる。
- **ファイルを変える仕事を並列にするなら、子ごとに作業場所（git の worktree、別のブランチ）を分ける。** 同じ作業場所では、触るファイルが違っても、ビルド・テスト・コミットがぶつかる。更新履歴・版の番号・lockfile のような、どの子も触る共有のファイルは子に書かせず、まとめる側が最後に1回書く。
- **子に何ができるかは、子の道具だけでなく、子から届く先まで数える。** 読み取り専用の子でも、書き込める別のエージェントや bot に頼める経路（チャットへの投稿、Issue や PR のコメントで動く仕組み、それができる MCP）を持てば、書き込めるものとして扱う。止めたいものは依頼文で禁じるだけで済ませず、立てるときに道具ごと外す。

## 2. どの重さのモデルに任せるか

モデルの名前で覚えない（増え、消え、地域で使えないことがある）。仕事の重さで層を選び、その場で使えるものを見て決める。

| 仕事 | 層 |
|---|---|
| 探すだけ・抜き出すだけ（場所の特定、一覧づくり、ログやテストの出力の要約） | 一番軽い層 |
| 範囲のはっきりした調べ物、文脈を持たない読み手 | 中間の層 |
| 判断が要る仕事、コードを書く仕事（機械的な書き換えも）、レビュー | 上位の層 |
| 上位の層で effort を上げても解けないとき | 最上位の層（既定にしない） |

- コードを書く仕事は、機械的な書き換えでも下の層に下げず、effort（考える量）を下げる。軽い層が読み違えると、その回り道を上の層が払う。
- モデルを上げる前に effort を上げる。
- 既定は任せる側と同じ重さ。軽い仕事は下げ、行き詰まったときだけ上げる。下の層に回すのは、間違えてもすぐ気づける仕事（ファイルを探す、ログやテストの出力を読む）。
- effort を上げて減るのは、エッジケースの見落としと確かめの不足。やり方そのものが違うときは effort では直らないので、別の提供元の目か、方針の見直しに回す。
- 一番軽い層に、欠陥を探すレビューや不具合の診断を頼まない。見落としが増える。
- 別の目が要るときは、別の提供元のモデルにする。同じ提供元の別の大きさは、同じ思い込みをしやすい。
- 使うモデルは依頼のたびに明示する。引き継ぎ方は道具で違い、明示しないと意図より弱いモデルで走ることがある。

## 3. 依頼文に書く

再調査させずに済む分を書く。自分の言葉で書くのは目的・終わりの条件・不変条件で、ほかは毎回同じ形でよい。

- **目的と終わりの条件**：何ができたら終わりか。終わりを機械で判定できる仕事は、その判定を条件にする（「`<古い呼び方>` の検索の該当が 0 件」「テストのコマンドが 0 で終わる」）。機械で判定できない仕事（見た目をそろえる、など）は、許す差と、回数か時間の上限を書く。無いと、測るたびに新しい差が見つかって終わらない。許す差が決まっていなければ、案を添えて人に1回確かめる（返事を待つ間は案の線で進める）。
- **分かっている落とし穴と参照**：試しで見つかったこと、同じ流儀の既存の実装、正本の docs。
- **作業場所と受け持ち**：作業場所の絶対パスとブランチ、受け持ちの範囲（フォルダー・ファイル）。並列なら、ほかの子も同時に動いていること。受け持ちの外の変更はほかの子のものなので戻させない。止めて報告させるのは、受け持ちの中に覚えの無い変更を見たときだけにする。
- **検証**：走らせるコマンド。コミットさせるなら、検証はコミットのあとに、変更の残っていない状態で走らせ、そのときの HEAD を書かせる（検証のあとにコミットすると、緑が今の中身を指さない）。依頼に無い、テストを消す・skip する・mock に置き換える・期待を緩めることは禁じ、要るなら止めて報告させる。
- **記録**：リポジトリに記録の定めがあれば従わせる。無ければ、更新履歴・PR 本文に書かせるのは、読む人が判断に使うこと（何が、どの条件で、どれだけ変わるか）。変更の中身を手で数えた数（変わる箇所の数など）は書かせない。直すたびにずれる。数が要るなら、どのコミットでどう数えたか（コマンド）を添えさせる。
- **禁止と止まる所**：push、PR、マージ、本番への接続、破壊的な操作、範囲外の変更のうち任せないもの。force push が要る場面と、設計の判断が要る場面では、止めて報告させる。依頼文の禁止は守りにならない（読み違えも、断りなく越えることもある）。本当に止めたいものは、渡す道具・権限・資格情報で止める。
- **さらに任せさせるか**：させるなら、目的・不変条件・禁止を孫への依頼にもそのまま写させる（要約のたびに条件が落ちる）。
- **報告の形**：先頭に状態を一語で（済んだ・懸念つきで済んだ・止まった・材料が足りない）。コミット、走らせたコマンドと終了コードとそのときの HEAD、計画からの逸脱とその場の判断と理由、実行した変える操作の一覧、確かめていない所、後始末。長さの目安も書く（そのまま返させると、任せる側の文脈を食う）。
- 子が自分の指示ファイルを読まない道具もある。効かせたい決まり（返す言語など）は依頼文に写す。

## 4. 受け取る

- **報告は入力にすぎない。** 「完了」「テストは通った」「0 件」は、実物で確かめるまで事実として扱わない。返ってきた diff は全部読む。
- **終わりの条件を自分で測り直す。** 残りの件数を数え直す、テストを今の HEAD で走らせ直す。報告の数をそのまま写さない。緑に数えるのは、コマンド・終了コード・HEAD がそろい、変更の残っていない今の HEAD で走ったものだけ。起動に失敗した検査と、構文だけの確認は数えない。
- **判定に合わせた抜け道が無いかを diff で見る**：テストの削除・skip・mock への置き換え・期待の緩め、警告を黙らせる注釈、設定でルールを切ること。
- **子が何を実行したかを見る。** 読み取り専用で頼んだ子も、実行したコマンドの一覧やログを見る。変える操作が混ざっていたら、結果の報告より先に、何が起きたかを人に伝える。リポジトリを読ませるなら、変更の無い作業ツリーで走らせて起動前の HEAD を控え、終わったら HEAD が同じで `git status --short` が空かを見る。変更の残る作業ツリーでは、同じファイルへの2度目の書き込みや、追跡していないフォルダーへの追加が status に出ないので、別の作業ツリーが要るなら対象のコミットから作る（`git worktree add --detach <絶対パス> <SHA>`）。ignore されたファイル・作業ツリーの外・ほかのブランチ・push は、どちらでも見えない。書き込みを止めるのは渡す道具で、これは止まっていたかを見るだけ。
- **指示と違うことをしていたら、まず理由を読む。** 子が正しいこともある。
- **後始末**：作業場所、一時ファイル、ブランチ。
- **人への報告は、確かめたことと確かめていないことを分ける。** 確かめたことは、どのコマンドで何が出たかを添える。人に決めてほしいことがあれば、それを先に書く。

## 5. 長い仕事・回し続ける仕事を任せる

何時間も走る仕事、セッションをまたぐ仕事、定期に起動する仕事は、上に加えて次を依頼文に入れる。

- **状態は会話の外に置かせる。** 進み・残り・その場の判断（理由と、外れていたときの影響）を1か所に書かせ、区切りごとに更新させる。置き場は、リポジトリや手元に引き継ぎの定め（Issue や PR のコメント、決まったファイル）があればそれに従わせる。無ければ、作業の PR か Issue のコメントに書かせ、子が PR や Issue に書けないときだけ、作業ブランチの1つのファイルにしてコミットさせる。このファイルは、任せた側がマージの前に消す。文脈が要約されても、別のセッションが引き継いでも続けられる。
- **終わりの条件は機械で判定できる形にし、回数か時間の上限と組にする。** レビューの指摘の数は条件にしない（直すたびに新しい指摘が出て終わらない）。
- **回る仕事は、意図ではなく判定に合わせて進む。** テストを消せば緑に、lint の抑止の注釈を書けば 0 件になる。終わりの条件の文に「テストを消さず、skip・mock・期待の緩め・抑止の注釈・ルールを切る設定の変更を足さずに」も入れ、始める前の HEAD を控えさせて、最後にその差分を見せさせる。
- **止まる条件を書く。** 原因の同じ見立てで2回直して直らなければ止める。設計の判断が要るもの（振る舞いが変わる直し）は、直さずに残して報告する。
- **出し先**：結果は PR か票に出させ、main に直接入れさせない。同時に開く PR の数にも上限を置く。
- 止め方（何を打てば止まるか）は道具で違う。始める前に人に伝える。

## 6. 別の目に頼むとき

違う提供元のモデルの目は、欠陥を探すレビュー、自分で2回試して行き詰まった不具合の別の診断、設計の選択への反対意見の場面でだけ使う。定例のレビューと、自分の作業の検算には使わない。頼むときは自分の見立てを渡さず（渡すと確かめて返ってくる）、変更そのものと不変条件だけを渡す。返った指摘は1件ずつ実物で確かめてから直す。

## 例

頼み：「200 ある設定ファイルを新しい形式に書き換えて。子で手分けして」

1. 3ファイルだけを1体の子に任せる。報告で「古い形式には、省略すると既定値が入る項目があり、新しい形式は省略を許さない」と分かる。
2. 残りを4体に分ける。依頼文には、作業場所（子ごとの worktree）と受け持ちのフォルダー、省略された項目の補い方、終わりの条件（古い形式の検索が 0 件、検証のコマンドが 0 で終わる）、検査を緩めない・要るなら止める、報告の形（状態・コミット・コマンド・終了コード・HEAD）、更新履歴は書かないこと、を書く。
3. 受け取ったら、各ブランチの diff を読み、古い形式を数え直し、まとめたブランチで検証を走らせ直す。更新履歴を1行足して PR にする。
4. 人には、確かめたこと（検索の件数、検証の結果と HEAD）と、確かめていないことを分けて報告する。
