# 敵対レビュー

自分の検算ではない。意図を知らない目で、作った側が「正しく動く」と思い込んでいる所を壊しに行く。自分の作業の確認は自分でやり、そのためには回さない。

## いつ回すか

- リポジトリが定める条件に触れたとき（例：数値の計算、テナントの境界、migration、元に戻せない操作、ガードや検査そのもの）。
- 定めが無ければ、壊れても他の検査が緑のまま通るもの、本番のデータ・お金・公開物に届くもの。
- 見た目の良し悪し（画面・図の見え方）は、敵対レビューで決めない。レビュアーには見えないので、プレビューをユーザーに見せて決める（画面の見え方は、実際に使う人が見て決めるのが確か）。見た目を変える変更で回すなら、計算・境界・データのような、見えない所に絞る。
- 普通の差分のレビューで足りる規模なら、組み込みのレビュー（Claude Code の `/code-review`、Codex の review など）を使う。
- 機能追加の PR ごとに定例で回さない。上の条件に触れる変更に絞る。

## 頼み方

- 渡すもの：対象（ブランチと起点・終点の SHA、または PR）、関係する不変条件（守る条件を文で書き、正本の ADR・docs・ガードのヘッダは出典として添える）、リポジトリが許す差（見た目の差の下限など。決めていれば）、走らせてよい検証コマンド。
- 不変条件として渡すのは、破れると使う人に実害が出るものだけ（下の「Important の線」）。「記録の数が振る舞いと合う」「見た目の差が 0」のような条件や、正本の文書を丸ごと不変条件として渡すと、それに反するものが全部 Important になり、巡が終わらない。
- 読み取り専用で起動すると、検証コマンドは走らないか、書き込みを伴うもの（テストやビルドの多く）が落ちる。そのときは頼む側が走らせ、コマンド・終了コード・出力の要所・そのときの HEAD を渡す。渡すものの細部と、レビュアー自身に走らせるときの使い捨ての worktree の作り方は [references/running.md](references/running.md)。
- 渡さないもの：実装者の意図、「こう直したつもり」の説明、自分の見立て。意図を知ると、同じ思い込みで読む。
- 相手：作った本人と別のエージェント。別の提供元のモデルが使えるならそれにする。答えは報告だけにさせ、書き込みは、上の検証のための使い捨ての worktree に限る（それ以外は読み取り専用）。読み取り専用は依頼文ではなく起動のしかたで決める。
- 相手がこの Skill を読むとは限らない（ほかの道具の CLI、Skill を読まない子。Kiro の custom agent は Skill の名前と説明しか持たず、MCP を持つ定義では起動の直後に一覧が空のこともある。どちらも `--agent` で起動したセッションでの観測で、委譲で起動した子では見ていない）。下の「Important の線」「レビューする側」「出力」の要点を依頼文に写す（2巡目以降は、下の「2巡目以降」の出させ方も）。Claude Code の `readonly-reviewer` は、定義でこの Skill を読み込んで始まるので、写さなくてよい。Kiro と Antigravity の `readonly-reviewer` は、本文でこの Skill を開くよう指示してあるが、子が `~` や環境変数を解けずに開けないことがあるので、要点を依頼文に写し、開いたかは返事で確かめる。
- 1巡目は深刻度で絞らせない。Important か Nit かを付けたうえで全部出させる。「重要なものだけ」と頼むと、報告が本当に減る（2巡目以降は、下の「2巡目以降」のとおり意図して絞る）。

## Important の線

指摘には、使う人への影響で Important か Nit かを付ける。Important は、マージの前に直さないと使う人に実害が出る欠陥。Nit は、直す価値はあってもマージを止めないもの（ラベルは Claude Code の Code Review の docs の「Severity levels」の Important と Nit）。使う人には、利用者のほか、運用する人と、その指示・手順・検査・記録に頼る人やエージェントも入る。Code Review の docs の「Example REVIEW.md」も、Important を、振る舞いを壊す・データを漏らす・ロールバックを妨げるものに絞り、書き方・命名・リファクタは多くても Nit にしている。

- 実害の例：誤った値や結果を受け取る、見て分かる誤りや崩れ、データ・お金・公開物が壊れる・漏れる・失われる・戻せなくなる、守り（ガード・検査・権限）が効かないのに緑に見える、指示や手順のとおりに動いた人やエージェントが誤る、記録を読んだ人が判断を誤る（何が変わったか、戻せるか、どこを確かめるかを取り違える）。
- 定め：リポジトリの定め（REVIEW.md・AGENTS.md など）が Important を決めていれば、それが先。頼む側が文で示した不変条件に反するものは Important（出典として添えた正本の細部は、不変条件ではない）。ほかの定めに反するものは、その定めが防ぐ害がこの差分で起きるかで決める（Code Review も、CLAUDE.md の定めに反したものを、害に合った深刻度にする。同じ docs の「Use CLAUDE.md for project-wide rules」）。
- Nit にとどめるもの：見た目の差のうち、リポジトリが許す差より小さいもの（決めていなければ、拡大しないと見えない差）、判断を変えない記録のずれ（数の小さなずれ、言い回し）、書き方・好み。値や計算の結果の誤りは、小さくてもここに入れない（誤った値や結果は実害）。記録のずれは、Important に当たっても、記録を直すだけなら次の巡は要らない（下の「2巡目以降」）。
- Important にするには、失敗の筋書きを「誰が、どんなときに、何で困るか」まで書く。「どんなとき」は、実際の使い方で起こりうる入力・状態にする。起こりうると詰めきれないものは、Nit に下げずに PLAUSIBLE の Important にする。起こりうる道を書けない仮定の心配は Nit（仮定の心配に応えて直すと、作りすぎになる。Anthropic の「Redesigning source control at Anthropic」、2026-10-13。敵対レビューに応えて、別の社内サービスを疑う検証を足しすぎた例）。筋書きが書けても、Nit にとどめるものに当たれば Nit。
- 見た目の差で、見て分かるかを決めきれないものは、Nit にして「見た目」と添える（受け取る側がユーザーに見てもらって決める。下の「受け取る側」）。

## レビューする側

- 既定は懐疑。欠陥を具体的な失敗（入力・状態 → 誤った結果・クラッシュ → 誰が何で困るか）として組み立ててみる。組み立てられたら CONFIRMED、疑いは濃いが詰めきれなければ PLAUSIBLE。振る舞いについての主張は実装の `file:line` で示し、名前やコメントから推しただけなら PLAUSIBLE にとどめる（Code Review の docs の「Choose what to write in REVIEW.md」の、誤った指摘を減らす書き方の例）。
- 見つけたものは全部出す。軽微だから、意図的かもしれないから、本筋でないから、で伏せない。取捨は頼んだ側の仕事（2巡目以降の出し方は、下の「2巡目以降」）。
- 確度は CONFIRMED / PLAUSIBLE、影響は Important / Nit（上の「Important の線」）のラベルで表す。憶測を断定にしないことと、報告を減らすことは別。
- 変更全体（PR）の起点より前からあった欠陥も出し、「既存」と印を付ける（`git blame` や `git log -L` で、その行を入れたのが起点より前かを確かめる。2巡目以降も、修正の範囲でなく変更全体の起点で決める）。印が無いと、受け取る側が直す範囲を広げて巡が終わらない。Code Review も、PR が入れていない欠陥には Pre-existing と付ける（作者の誤りに見せないため。claude.dev の「How the Claude Code team does code review」、2026-10-15）。
- 同じ形の欠陥を1か所見つけたら、ほかの箇所も探して一緒に並べる。1か所ずつ直すと、次の巡で同じ欠陥の別の場所が出てくる（同じ記事）。
- 指摘を取り下げて場を丸めない。探し尽くして無ければ「無い」と言ってよいが、早じまいの口実にしない。
- 手順：差分を把握する → 変更したファイルとその周辺（呼び出し側・型・テスト）を読む → 不変条件の正本を読む → 検証コマンドを自分で走らせる（起動のしかたで走らせられないときは、渡された結果を読み、自分では走らせていないと出力に書く）。

## 出力

深刻度の順に全件（並べ替えであって、足切りではない）。1件ごとに、`file:line`、一文の要約、具体的な失敗の筋書き（誰が何で困るかまで）、Important か Nit か（Nit に「見た目」と添えるなら、それも）、CONFIRMED か PLAUSIBLE、既存ならその印と根拠（入れたコミット）。同じ形の欠陥は1件にまとめ、箇所を全部挙げる。最後に、走らせた検証とその結果、見きれなかった範囲（読めていないファイル、追えていない経路）。黙って「全部見た」ように見せない。2巡目以降は、下の「2巡目以降」の形にする。

## 受け取る側

- 一覧の `file:line` は「どこを見るか」までしか正しくない。1件ずつ実物を開いて確かめてから、直す・Issue にする・見送る（理由を書く）を決める。
- 報告が最後まで返らなかった巡（落ちた、時間切れ、枠切れ、読むための道具を拒まれた）は、指摘 0 ではなく判定なしとして扱い、走らせ直すか別のレビュアーに回す。見きれなかった範囲に変えたファイルが入っていれば、そのファイルも判定なし（Code Review の docs の「Read the result from a script」も、判定の行が無い結果を、指摘 0 でなく判定なしと読ませる）。
- Important かどうかも、上の「Important の線」で確かめる。筋書きに誰が何で困るかが無いもの、見た目の差のうち見て分からないもの、判断を変えない記録のずれは Nit として扱い、打ち切りの数に入れない。下げたものは、理由と一緒に PR に並べて残し、あとで人が見て戻せるようにする（受け取る側の Claude は、見つけた問題を大したことはないと自分で言いくるめやすい。Anthropic の「Harness design for long-running application development」、2026-03-24。評価役の Claude が、正しい問題を見つけたあとで大したことはないと判断して通した例）。
- 「見た目」と添えた指摘は、直す・Issue にする・見送るを決める前に、まとめてプレビューを1回見せ、見て分かるかをユーザーに決めてもらう。見て分かると言われたものは Important として扱う（上の「Important の線」の、見て分かる誤りや崩れ）。
- Nit はマージを止めない。表記だけで直せるならその場で直す。直すのにロジックを変える Nit は、巡の中では直さず、Issue に回すか見送る（直すと次の巡が要り、それがまた指摘を生む。作者がエージェントだと、人なら流す Nit も直してしまい、コミットとレビューの巡が増える。claude.dev の同じ記事。下の「2巡目以降」）。Important を直すついでにも直さない。
- 同じ形の欠陥としてまとめられた指摘は、挙がった箇所を全部直す（挙がっていない同じ形の箇所も自分で探す）。
- 「既存」の印の付いた指摘は、この変更の範囲で直すか、Issue に回すかを分けて決める。直す範囲を黙って広げない。
- 同じ種類の指摘が、巡や PR をまたいで何度も出るなら、出た所を直すだけで終わらせない。lint の規則、テスト、Skill や指示ファイル（リポジトリの `REVIEW.md` や AGENTS.md に、そのリポジトリで Important にする実害と、レビューから外すパス（生成物など）を短く書く、など）で、元から出ないようにする（claude.dev の「How the Claude Code team does code review」）。
- 直さなかった指摘（Issue に回した・誤り・意図どおり・直す価値なし・Nit に下げた）は、要旨と理由を PR に残す。あとで人が見て判断を戻せるようにするためで、件数の内訳は数えない（数えた数は直すたびにずれる）。
- 意図を渡していないので、「正しく実装された、間違ったもの」は見つからない。仕様に合っているかは受け取る側が見る。

## 2巡目以降

- 指摘を受けてロジックを直したら、範囲を「直近の修正コミットが何を壊したか」に絞って、もう一度回す。指摘が無かった、見送った、記録・コメント・表記だけを直した、のときは要らない。指示や設定の文書で条件・権限・コマンドを変えたのは、ロジックの修正に数える。
- 2巡目以降は、Important は「出力」の形のまま、Nit は `file:line` と一文だけ（「見た目」と添えるなら、それも）を出させる。受け取る側は、2巡目以降の Nit に手を付けなくてよい（確かめるのは、Important の取り違えに見えるものと、「見た目」と添えたものだけ）。
- 打ち切り：修正のあとの巡で、未解消の Important と、新しく見つかった既存でない Important がどちらも 0 なら、頼んだ側が打ち切ってよい（その巡で初めて見つかった既存の Important は、Issue に回すか理由を残して見送るまでは数える）。3巡目でもロジックを直す Important が残るなら、続けるか止めるかを人に返す。「指摘が 0 件になるまで」を条件にしない。

2巡目に渡すもの、レビュアーに前巡の指摘をどう分けさせるか、打ち切りの細かい条件、Nit を絞る理由は [references/later-rounds.md](references/later-rounds.md) を読む。
