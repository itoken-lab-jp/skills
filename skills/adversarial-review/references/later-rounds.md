# 2巡目以降

SKILL.md の「2巡目以降」の細部。


## 進め方

- 指摘を受けてロジックを直したら、1巡で終わりにしない。範囲を「直近の修正コミットが何を壊したか」に絞ってもう一度回す。指摘が無かった、見送った、ロジックを変えずに記録・コメント・表記だけを直した、のときは2巡目は要らない。指示や設定の文書で条件・権限・コマンドを変えたのは、ロジックの修正に数える。起点と終点の SHA を明示し、追跡済みの範囲外は名指しで外す。絞らない巡は、1巡目からあった欠陥を巡ごとに少しずつ見つけ続けて、終わらない（claude.dev の「How the Claude Code team does code review」は、繰り返し指摘されたものに git blame をかけると約 59% が1巡目の時点からあったコードで、新しいバグはまれだったと書き、最初の数巡のあとは差分だけを見直すようにした）。
- 2巡目以降は、Important はSKILL.md の「出力」の形のまま、Nit は `file:line` と一文だけ（「見た目」と添えるなら、それも）を出させる。受け取る側は、2巡目以降の Nit に手を付けなくてよい（確かめるのは、Important の取り違えに見えるものと、「見た目」と添えたものだけ）。欠陥を探せと頼まれたレビュアーは健全な作業にも何か出すので、全部追うと作りすぎになる（Claude Code の best practices の「Add an adversarial review step」は、正しさと示した要件に効く穴だけを出させ、ほかは任意として扱うよう書く）。Code Review も、あとの巡は前の巡からの変更に絞り、Nit と既存の指摘を減らして、出さなかった数を要約に書く（Claude Code の Code Review の docs の「What a later review covers」）。
- 2巡目に渡すもの：前巡の報告（指摘の本文）、直さなかった指摘ごとの受け止め方（Issue に回した・誤り・意図どおり・直す価値なし）と理由（Nit に下げたなら、そのことも）、修正の起点と終点の SHA、変更全体の起点の SHA（「既存」を決めるため。コマンドが走らない起動なら、SKILL.md の「頼み方」の blame の出力（細部は running.md）も）、不変条件（文で）、検証コマンド（読み取り専用で起動するなら、頼む側が走らせた結果）。直した側の「どう直したか」の説明は渡さない。レビュアーには、前巡の指摘を 1 件ずつ「解消／未解消／理由つきの見送り」に分けさせ、見送りの理由が成り立たないと見るなら、未解消に入れて、その筋書きを書かせる（新しい欠陥を探すだけだと、直りきっていない指摘を取りこぼす。理由を渡さないと、見送ったものが全部「未解消」に見える）。同じレビュアーを続けて使ってよい（前巡の指摘が直ったかを確かめやすい）。別の目も欲しいときは、新しいレビュアーに前巡の報告を渡す。
- 打ち切り：修正のあとの巡で、未解消の Important（見送りの理由が成り立たないとされたものを含む）と、その巡で新しく見つかった既存でない Important（修正で入ったものに限らず、前の巡で見落とされていたものも）がどちらも 0 なら、頼んだ側（AI）が打ち切ってよい（既存の欠陥は、Issue に回すか理由を残して見送ったあとで数から外す。その巡で初めて見つかった既存の Important も、そのどちらかを済ませるまでは数える）。残った Important が、ロジックを変えずに直せるもの（記録・コメント・表記）だけなら、直して打ち切ってよい（次の巡も、人への確認も要らない）。記録やコメントを実装に合わせて書き換えてよいのは、記録の方が誤っていたときだけ。実装が約束を破っているのに、約束（記録・コメント・指示の条件）の方を狭めるのは、ロジックの修正に数える。3巡目でもロジックを直す Important が残るなら、続けるか止めるかを人に返す（claude.dev の「How the Claude Code team does code review」も、3巡のあとは、作者にやり方を考え直させる）。「指摘が 0 件になるまで」を条件にしない（直すたびに新しいコードができ、それがまた指摘されて終わらない）。PR には、回した巡の数、直さなかった指摘と理由、打ち切った理由を残す。
