# Git の作業手順

AI に git の作業を任せると、コマンドはそつなく打てる。外しやすいのは、打ったあとに実物を見ない所で、次の形になる。

- `git status` が片付いているのを見て安心し、ブランチに前から入っていた別のコミットに、push して PR を出してから気付く。
- 秘密の入ったファイル（`.env` など）をコミットに入れないだけで、それが ignore されていないことを言わない。次の人が `git add -A` で入れる。
- PR を出して終わり、CI の結果を見ない。マージのあとも、デプロイの成功を見て終わり、本番そのものを見ない。
- CI の費用を、ワークフローの設定や README から推測で答え、実際の請求を見ない。

先にリポジトリの決まりを読む（CONTRIBUTING、AGENTS.md や CLAUDE.md などの指示ファイル、PR のひな形、コミットメッセージの決まり、`git log --oneline -10` の書き方）。誰がどの条件でマージしてよいか、PR を draft で出すか、マージが本番に出ることになるか、もそこで分かる。以下は決まりが無い所の既定。

## 1. 始める

- 作業の前に、同じことをしている PR やブランチが無いか、頼みの元の票（Issue など）に後から書き込みが無いかを見る。
- 新しい作業は、手元の main ではなく、取ってきた最新の main（`git fetch` → `origin/main`）から切る。並行して別の作業が動いている所では、作業場所を分ける（`git worktree add`）。1人で使っていてリモートも無いリポジトリなら、その場で作業してよい。
- 始める前に試験を一度走らせ、もとから落ちている試験があれば分けて覚えておく。あとの失敗が自分のせいか分からなくなるため。

## 2. コミット

- コミットの前に試験を走らせ、通るのを見る。`npm test | tail` のようにパイプでつなぐと、落ちても終了コードが 0 になって次へ進むので、結果を見てから次のコマンドを打つ。
- 入れる物は名前で選ぶ（`git add <パス>`）。`git add -A` や `git add .` は、一時ファイル、別作業の変更、秘密を拾う。入れたら `git diff --cached --stat` で並びを見る。
- 秘密（API キー、パスワード、`.env`、秘密鍵）を見つけたら、入れないだけでなく、どこにあり ignore されているかを頼んだ人に一言伝える。ignore を足すのは頼まれた範囲の外なので、足すかを聞くか、足したと書く。
- 1つのコミットは1つの意図にする。整形だけの変更と振る舞いの変更、ついでの直しは分ける。
- メッセージは、何をしたかを1行目に、なぜを本文に書く。リポジトリに決まり（Conventional Commits など）があればそれに従う。
- マージ・rebase・cherry-pick の途中（`git status` に出る）では、index にその操作の結果が入っている。ファイルを外したりコミットを分けたりせず、途中であることを頼んだ人に伝える。
- フック（pre-commit など）で落ちたら、直して同じコミットをし直す。`--no-verify` で飛ばさない。`--amend` は前のコミットを書き換えるので、頼まれたときだけ使う。

## 3. PR を出す前

- ブランチの中身は、作業場所ではなく main との差で見る：`git log --oneline origin/main..HEAD` と `git diff --stat origin/main...HEAD`。`git status` が片付いていても、前に入れた試しのコミットや別作業のコミットは見えない。
- 要らないコミットが混ざっていたら、push の前に外す。まだ push していないブランチは書き換えてよい（`git rebase --onto`、または origin/main から新しい名前のブランチを切って要るコミットだけ `git cherry-pick`）。外したら試験を走らせ直す。もう push して人が見ているブランチは書き換えず、外すコミットを足すか、頼んだ人に聞く。
- 差分を通しで読み、試行錯誤の回り道、要らない分岐、頼まれていない変更を削って、いちばん単純な形にする。
- PR の本文には、何が問題でどう変えたか、確かめたこと（コマンドと結果）、確かめていないこと、壊れうる所と戻し方を書く。リポジトリにひな形があればそれを埋める。

## 4. PR を出したあと

- CI の結果を、終わるまで見る（GitHub なら `gh pr checks <番号> --watch`）。待てないときは、まだ走っていることと、どこで見られるかを報告に書く。
- CI が落ちたら、最初のエラーから読み、自分の変更のせいかを見分ける。手元では通るのに落ちるなら、CI と同じ版（言語・依存）で再現する。再実行を繰り返して緑を待たない。自分のせいでない失敗（もとから落ちていた・外のサービスの不調）は、そうと分かる根拠を添えて伝える。
- レビューのコメントには、1件ずつ「直す」か「理由を返す」かを決める。直したら push してから、その件のスレッドの中で何を直したかを返す。解決（resolve）にするのは直したものだけで、理由を返したものはレビューした人が閉じられるよう開けておく。
- 作業中に main が進んだら取り込む。push 済みのブランチは `git merge origin/main`（rebase すると force push が要る）、まだ push していないブランチは `git rebase origin/main` でよい。
- ほかの作業ブランチの上に積んだ PR は、下の PR をマージしてブランチが自動で消えると、閉じることがある（GitHub なら `gh api repos/<持ち主>/<名前> --jq .delete_branch_on_merge` で自動削除の設定を見る）。積まずに順に main へ出すか、下をマージした直後に上の向き先を main に変える（`gh pr edit <番号> --base main`）。下をマージする前に向き先を変えると、上の PR に下のコミットがそのまま入り、下を squash したあとで同じ変更が二重に見える。

### 取り込みと衝突

衝突そのものはたいてい直せる。外しやすいのは、両立しない変更を黙って片方に決める所と、直したあとに試験を走らせない所。

- 直す前に、ぶつかった両方のコミットの文を読み、何のための変更かをつかむ。両方の意図を残す。
- 片方を採るともう片方の目的が壊れるときは、黙って決めない。頼んだ人に聞くか、採ったほう・壊れること・両方の理由を報告の最初に書く。両立のために設定や振る舞いを足したら、足したと書く。
- 衝突が無くても、取り込みのあとは試験を走らせる（片方が変えた名前を、もう片方の新しいコードが使っていることがある）。落ちた試験は、どちらの変更が正かを見て直す。
- 生成されるファイルは手で混ぜず、生成し直す。rebase で同じ変更が main に入り済みなら、そのコミットを落とす。
- 報告は、衝突した所と直し方、自分で選んだ所、試験の結果。単純な衝突なら1〜2行でよい。

## 5. マージ

- マージしてよいか（自分か人か、どの条件か）はリポジトリの決まりに従う。頼まれていなければマージしない。
- CI が終わって成功したのを見てからマージする。走っている途中で打たない。管理者の権限（`--admin`）や守りの規則を外す手で通さない。自動マージ（`gh pr merge --auto`）が待つのは、守りの規則で必須にした検査だけなので、必須の検査が CI の全部を覆っているリポジトリでだけ、待つ代わりに使う。
- 原則 squash でマージする。main の履歴の書き換えと force push はしない。

## 6. マージのあと（見届け）

マージが本番に出ることになるリポジトリでは、本番が自分の変更になるまでを見る。デプロイの成功だけでは、どのコミットが出たかは分からない。

1. デプロイの走り（GitHub なら `gh run list --workflow <名前>`）で、自分のマージのコミット（`gh pr view <番号> --json mergeCommit`）の走りを探し、終わるまで見る。
2. 自分の走りが取り消された（cancelled）ときは、同時に走らせない設定（`concurrency` の `cancel-in-progress` など）で、後から入った別のマージに譲ったことが多い。やり直す前に、後の走りのコミットが自分のコミットを含むかを見る：`git fetch` のあと `git merge-base --is-ancestor <自分のコミット> <後のコミット>`（含めば終了コード 0）。含んでいれば、後の走りが成功したときに自分の変更も出ている。
3. 最後に本番そのものを見る。health や version の口があれば、そこが返すコミットが自分のコミットか、自分のコミットを含むコミットかを確かめる。口が無ければ、変えた振る舞いを本番で1つ見る。
4. 報告には、出たかどうか、何で確かめたか、途中で起きたこと（取り消し・ほかのマージとの同乗）を短く書く。

本番で壊れたら、`git revert` の PR で戻す。main の履歴は書き換えない。直す PR は、戻したあとに落ち着いて出す。docs だけの変更で本番に出ない設定なら、デプロイが走っていないことを見る。

## 7. 片付け

- squash でマージしたブランチで続きをするときは、最新の main から切り直し、まだマージしていないコミットだけを載せ直す（squash したブランチのままだと、同じ変更が二重に見える）。
- マージしたら、作業ブランチと作業場所（worktree）を片付ける。squash でマージしたブランチは main の祖先にならないので `git branch -d` が断る。PR がマージ済みだと確かめたブランチなら `-D` で消してよい（中身は main に入っている）。`git worktree remove` が「変更がある」と断ったら、そこにしか無いファイルがある。`--force` で消さず、何があるかを見せて、残すか消すかを頼んだ人に聞く。
- 頼みの元の票（Issue）を閉じるのは、頼まれたことが全部済んだとき。公開や配布が残っているなら、マージだけで閉じない。

## 戻せない操作

次は、作業の消失や他人の作業の上書きにつながる。頼んだ人がその操作と対象を名指しで頼んだときだけ行い、行う前に何が消えるかを見せる。

- 共有のブランチ（main、人と一緒に使うブランチ）への force push、履歴の書き換え
- `git reset --hard`、`git clean -f`、`git checkout .` / `git restore .`（未コミットの変更が消える）
- マージしていないブランチの `git branch -D`、`git worktree remove --force`、`git stash drop`
- push が拒まれたとき（リモートが進んでいる）の force push。まず取り込んで、何が進んだかを見る

自分の作業ブランチへの通常の push、PR を出すこと、draft にすることは戻せるので、聞かずに進めてよい。守りたいことが決まっているなら、注意書きより仕組みで止める（ブランチの保護の規則、必須の CI、エージェントの道具のフックで危ないコマンドを止める）。仕組みを足したら、わざと破って止まるのを一度見る。

## CI の費用を調べる

費用は、ワークフローの設定や README・コメントから推測せず、実際の請求で見る。設定の上のコメント（「リリースのときだけ走らせる」など）は、設定が変わっても古いまま残ることが多い。

1. 請求を実行環境ごと（Linux・Windows・macOS、ランナーの大きさ）と日ごとに分けて見る。GitHub Actions なら `gh api "/users/<持ち主>/settings/billing/usage?year=<年>&month=<月>"`（Organization なら `/organizations/<名前>/settings/billing/usage`。`day` で日にも絞れる。`sku` で実行環境が分かれる）。比べる前の月も同じように取る。権限が足りなければ、持ち主に何の権限が要るかを伝える（`gh auth refresh -h github.com -s user` など）。macOS や大きいランナーは、同じ分でも単価が何倍も高い。月の初めは無料の枠から減るので、金額が 0 の日があっても無料とは限らない。
2. 増えた日を見つけ、その日の前後のワークフローの変更を `git log -p -- .github/workflows/` で見る（起動の条件、matrix、ランナー）。
3. どの job が時間を食っているかを、run と job の実際の時間で見る（`gh api repos/<持ち主>/<名前>/actions/runs/<id>/jobs`）。課金は job ごとに分へ切り上げられる。比べるときは、直近の成功した run の中央値で見る。run の一覧はページ送りで全部取る（1ページ最大 100 件）。`created` などで絞った検索は全体で 1,000 件までなので、超える期間は日ごとなどに分けて取る。
4. 直し方（起動の条件を絞る、matrix を減らす、同じブランチの古い run を取り消す、キャッシュ）を、減る見込み（分か金額）を添えて出す。どれにするかは費用を払う人が決めるので、ワークフローを書き換えるのは頼まれてから。

GitLab CI・CircleCI・Azure Pipelines なども、実行環境ごとに分の重みやクレジットが違う課金なので、同じ順で見られる（請求の画面か API、変更の履歴、job の時間）。

## 落とし穴

- Windows では改行の設定（`core.autocrlf`）で、全行が変わった差分になることがある。`.gitattributes` に従い、`git diff --stat` の行数が思ったとおりかを見る。
- 非対話の環境では、人の入力を待つコマンド（`git add -p`、`git rebase -i`、エディタが開く `git commit`）が止まる。`-m` やファイルで渡す。
- コミットの作者のメールは、推測で書かない。推測のメールが他人のアカウントに結びつくことがある。リポジトリの設定（`git config user.email`）か、頼んだ人に聞いたものを使う。
