# 具体と抽象を行き来する

AI は、抽象に上がる一歩はできる。指摘を「同じ種類」にまとめたり、事例から原則を立てたりする。外すのは、戻って確かめる一歩で、次の形が多い。

- 作った原則を、作るときに使った例にしか当てない。文書の残り、隣のファイル、別の場面に当てて確かめない。
- 原則が手元の例の言葉に縛られて狭くなる。「`retry(3)` の 3 が回数か秒か分からない」という指摘から、ほかの `retry` は直すが、`wait(500)` や `limit` という名前の同じ抜け（何の数か分からない）は見落とす。
- 直した箇所や差分を並べて終わる。次に使う人は、並んだ例に似たものしか拾えない。
- 逆に、原則だけを書いて例を捨てる。読み手は原則を新しい例に当てられず、例で当たっていた直しまで当たらなくなる。

LLM は規則を作るのは得意で、自分の規則を個々の例に当てるのが苦手だと分かっている。人でも、例が1つだと原則は別の場面に移らず、2つ以上を比べると移る。だから、作った原則は当ててみるまで仮のものとして扱い、当てた結果で直す。

## 1. 上がる：理由を1文にして、比べる

- 例（直された箇所、事例、差分）ごとに、何を変えたかでなく、なぜ変える必要があったかを1文で書く（「`retry(3)` を `retry({ times: 3 })` に」でなく「読み手が 3 を回数か秒か決められない」）。
- 2つ以上の例を並べ、理由の共通点を原則にする。例が1つしかないときは、ありそうな別の場面を自分で2つ作って比べる。
- 原則を、例に出てくる言葉を使わずに言い直す。言い直せなければ、まだ例の一覧にとどまっている。
- 高さを合わせる。新しい1文を見て、当たるか当たらないかを決められる高さにする。低すぎると言葉の禁止になる（「`retry` の引数に名前を付ける」）。高すぎると何も決められない（「読みやすく書く」）。ちょうどよい例：「数には、何の数か（単位・対象）が読み手に分かる形を付ける（文脈で一つに決まるときは省いてよい）」。

## 2. 下りる：作るときに使っていない例に当てる

- 当てる先は、作るときに使っていない例にする。文書やコードの残り、同じフォルダーのほかのファイル、次に使う予定の文章、違う分野の場面を自分で2つ。
- 探すときは、例の言葉でなく原則の意味で探す（「何の数か」の抜けなら、`retry` に限らず、名前の無い数・単位の無い設定値・`n` や `limit` のような名前も拾う）。
- 当たらない側の例も1つ探す（文脈で一つに決まる、決まりや仕様として言い切るべき所など）。そこは変えない。
- 当たった所は、手元で分かる範囲で直す。直すのに要る事実（数字・連絡先・名前など）が手元に無ければ、作らずに印（【要確認】など）を付けて残し、報告で聞く。当たったのに黙って元のまま残さない。
- 当たった所、当たらなかった所を短く控える。

## 3. 直す：外れた所で原則を変える

- 拾うべき所を拾えなかったら、原則を広げる。拾ってはいけない所を拾ったら（文脈で一つに決まる、意図した書き方）、当てはまらない場合を原則に書き足す。
- 直したら、前に当たっていた例が外れていないかを見る。
- 止めどころ：当てて直す一巡で原則が変わらなければ止める。変わり続けても3巡で止め、残った迷いを報告に書く。

## 4. 残す：原則に例を1つ付けて戻す

- 手引き・学び・チェックリストに残すときは、原則ごとに、典型の直す前と後の例を1つ（多くて2つ）と、当てはまらない場合を付ける。
- 骨組みは原則で組み、事例は原則の下に置く。事例ごとの節（「A 社の場合」「B 社の場合」）にしない。
- 作るときに使った例しか知らない読み手でも、新しい例に当てられるかを最後に見る。

## 5. 手間は頼みに合わせる

- 1か所だけの決まった直し（名前の変更、誤字、指示どおりの書き換え）では、この手順を回さない。そのまま直して短く報告する。
- 指摘を文書全体に生かす、事例から手引きを書く、学びを残すといった頼みで使う。報告には、取り出した原則と、どこに当てて何を直したか、迷って残した所を書く。原則の講釈は長くしない。
